# Delivery and validation

Build the first release around direct-managed search and indexing Pods, the shared object store, predictable multi-AZ replacement, and two stable role Services. Qualify EKS and GKE Standard independently. A successful source test or controller unit test establishes a specific contract. Cloud node maintenance, routing convergence, TLS and workload throughput require end-to-end evidence on the chosen platform.

## Implementation order

| Milestone | Deliverable | Evidence required to advance |
| --- | --- | --- |
| 1. Java workload contract | Build the pinned serverless shell image. Ship a launcher with explicit JVM options, image digest, paths, security providers, role/AZ settings and signal behavior. Record the startup and live setting catalogs for that image. Define the node-local lease and warm-up results. | JVM receives `SIGTERM`, a remote peer can reach its advertised address, node roles are correct, and the image can ingest and search against a disposable qualified store. Failed first lease publication cannot satisfy serving qualification. |
| 2. Namespaced controller and reusable library | CRD schemas, controller deployment and scoped RBAC, deterministic Pod planning, two Services, per-group PDBs, immutable rendered config, and recovery status. | Unit tests cover planner inputs and invariants. Integration tests cover ownership, conflict, retry and controller restart, with one plain consumer proving the library has no Java dependency. |
| 3. Role/AZ placement and provider qualification | Dedicated placement profiles, admitted Pod fit calculation, provisionable Pod bounds, role-specific warm reserves, and per-provider configuration examples. | EKS and GKE Standard place each role on qualified nodes in its assigned AZ. Failed fit stops new demand. Observe a real drain of a direct-managed Pod, verify PDB and signal behavior, and prove ordinary autoscaler scale-down preserves warm nodes. |
| 4. Planned lifecycle and traffic | Graceful drain, rolling replacement, warm gate for strict policy, health-qualified ingress routes and one-AZ recovery. | Stage a replacement while maintaining role/AZ floors. Demonstrate read and write behavior under whole-AZ hard loss and failback with the actual ingress and measured store load. |
| 5. Safe shared-store blue/green | Preview Services, revision compatibility validation, explicit promotion and rollback operations, retention and crash recovery. | Show both revisions interoperate, qualify actual traffic before and after both selector changes, and verify rollback after newer writes on a disposable bucket. |
| 6. TLS and packaging | BYO certificate support, optional issuer integration, leaf and CA rotation, release/install artifacts, and platform and on-call procedures. | Fresh HTTPS and native peer handshakes pass through rotation, including mixed versions and blocked surge. Verify the trust boundary and scoped RBAC. Publish supported Kubernetes, provisioner and Java image versions only after the matrix passes. |

Decouple dependency work where practical. For example, the planner tests can use a fake application eligibility adapter while the Java image is being qualified. Treat transport mTLS, storage compatibility, and actual runtime readiness as requirements for exposing the production deployment. Software support starts with measured passing combinations. Optional weighted fleets, automatic role scaling, a GCP Karpenter adapter, and TLS hot reload can have separate release gates. [Research feature inventory and reference operator comparison](../research/operator-feature-inventory.md)

Retaining the primary bucket protects against an operator deleting durable data during fleet cleanup. An optional snapshot repository reference selects a Java-native repository. Scheduled snapshots, verified restore and backup into an independent recovery domain still require their own workflows. Hard per-index AZ policy, explicit pre-termination writer drain, and stock OpenSearch administration integrations also need separate Java or controller contracts. [Snapshot repository parameter](api-and-resources.md#snapshot-repository-parameter) · [Follow-on features and their dependencies](../research/operator-feature-inventory.md#follow-on-features)

## Tests and acceptance criteria

Use unit tests for desired-state validation, fit and policy arithmetic, and for the generic planner. Use an API integration harness to check owned-object intent, conditional writes, operation status, schedules, and PDB wiring. Validate admission-injected resources and scheduler behavior in a disposable Kubernetes cluster. Use real provider environments for Karpenter, GKE repair and AWS ALB tests. A local multi-zone label simulation covers controller policy and Java placement. It cannot establish provider drain timing or AZ failover behavior.

| Scenario | Evidence to collect |
| --- | --- |
| Same-zone rolling replacement | Under traffic, the new Pod has the requested AZ, approved image and valid serving state before old retirement. A cold or absent successor prevents a planned floor violation. Include one Pod per host, sidecars, max surge and pending limits. |
| Custom runtime and cluster settings | Verify shared and role-specific arg rendering, exact values with spaces or literal `$()`, rejected reserved keys, typed heap sizing and role-only revision changes. Persist a supported live setting and verify its effect after refresh. Test removal, unsupported keys, an ambiguous write response, and separation between live settings and blue/green rollback. [Configuration design](runtime-configuration.md) |
| OCI plugins | Apply a spec that references an approved bundle in a private registry. Verify automatic download and installation on the first Pod and a replacement, then exercise the feature through OpenSearch. Verify partial fetch and init retry behavior, digest and signature failures, invalid archives, plugin dependency conflicts, and effective Pod fit. Exercise changes across mixed fleets and verify rollback with the retained artifacts. [OCI plugin contract](oci-plugins.md) |
| Primary S3 remote store | Resolve a named repository to a pre-created bucket. Verify search and indexing use it for ordinary writes, reads and recovery with the bundled S3 implementation. Exercise invalid references, denied bucket access, an attempt to redirect the repository, replacement of a Pod, and blue/green reuse of the same store. [Primary S3 remote store](api-and-resources.md#primary-s3-remote-store) |
| Concurrent or stale lifecycle actions | Restart after create, after gate release and after eviction admission while the hook or JVM is terminating. Race an external eviction for the last PDB allowance. A denied operator eviction must leave its victim's search role serving. Verify no duplicate retirements and preserve newly bound Pods and same-name replacements with another UID. |
| `NodeClaim` fit and runaway cases | Exercise prediction above registered allocatable, increased DaemonSet requests and surge overlap, a Pod-slot shortfall, missing hostname on a matching node, a mismatched startup taint and capacity exhaustion in the required AZ. Validate admission-added resources before gate release. Measure demand until withdrawal and late nodes already in flight. |
| Warm reserve and consolidation | On EKS use `WhenEmpty` and verify a lightly loaded warm Pod stays while an eligible empty host can be collected. On GKE verify scale-down protection on initial Pod creation and eligible cleanup after intentional deletion. Exercise drift, ordinary upgrade and repair independently from autoscaler consolidation. |
| Readiness, ingress and propagation | Simulate warm-up success, timeout, partial copy, no usable peers and same-Pod JVM restart while the controller is delayed and a custom condition still reads true. Verify the strict process-local probe prevents premature PDB admission. Fail an ingress node and an OpenSearch node separately. Measure timeouts, ALB 5xx, target 5xx and the end-to-end client error window. |
| Loss of the largest AZ | From peak load, partition or stop an entire AZ with failed-zone requests already occupying pending slots. Verify bounded withdrawal, survivor admission and separate warm-up accounting even when Pods bind quickly or become Ready before copying stops. Race voluntary drains in both surviving zones and verify the reported local and role-wide limits agree with their actual enforcement. Record routing time, search latency, expiry, fencing, replay, failback and acknowledged versus unknown writes. |
| Object-store slowdown and outage | Apply throttling and errors independently of node availability. Serving capacity and recovery status reflect the dependency failure. JVM liveness and controller logic avoid a synchronized restart loop. Verify bounded warm-up, replay and request load. |
| Blue/green and rollback | Test insufficient candidate capacity, image incompatibility, conflicting approvals, conditional update races and restart between role switches. Approve a rollback using the mixed expected mapping and verify only switched routes change. Check receiving fleet and executed-peer evidence separately. For direct ALB integration, exercise pre-registering candidate target groups and clearing listener health gates while the old target groups stay registered. |
| TLS and sidecars | Test invalid or stale leaf input, issuer outage, leaf replacement, CA overlap and removal, and expiry on retained fleets. Use fresh mutual and HTTP handshakes. Distinguish ALB encrypted target connections from identity-verified application links. Verify sidecar resource accounting and dependencies during Java startup and shutdown. |
| Dynamic security configuration | Verify built-in account update, removal and cache behavior during a store outage. Qualify in-place policy changes with a delayed consumer, a restarted process, a retained fleet and failed revocation. Verify that an ordinary reload leaves Pod UIDs and process incarnations intact. [Security acceptance](security-reload.md#revocation-and-acceptance) |
| Instance deletion and re-creation | Verify the explicit decommission sequence, then exercise direct CR deletion with foreground garbage collection and namespace teardown. Document the cleanup ordering that those paths can interrupt. Preserve external bucket and credentials in every case. Verify reattachment after clean and abrupt loss of local state. |

Record platform, Kubernetes and provisioner versions, Java image digest, node shapes, target counts, client load distribution, object-store backend and qualification data for each run. Measure time to healthy routing, time to recover affected writes, search p95/p99 and cache/store amplification. Set numeric service and recovery targets with the deployment owners before calling a scenario qualified. Hard failures can interrupt in-flight work. A measurement of no errors in one steady-state run does not establish a zero-error failover guarantee. [Java pilot and harness evidence](../research/java-serverless-operations.md#evidence-in-the-branch) · [Platform deadlines and failure paths](../research/node-disruption-recovery.md)

## Operational ownership

| Symptom | First trustworthy evidence | Decision |
| --- | --- | --- |
| Pending replica | Group target, admitted Pod requests, last scheduler failure, profile qualification and launch evidence where available | Distinguish expected shortage, hard placement restrictions and prediction mismatch. The operator limits or withdraws demand. Platform owns node remediation. |
| Stalled rollout | Active operation UID and phase, role/AZ serving count, candidate startup and local lease evidence, PDB status | Keep healthy capacity. Continue a durable operation only against the recorded intent and current floors. |
| Warming or cold search | Per-process warm-up outcome, peer coverage, end-to-end query latency and object-store usage | Keep strict rollout gates in place. Use the selected degraded-serving policy during genuine cold recovery and display the warm deficit. |
| Requests fail during a zone loss | Actual role Service selectors, ingress and ALB health, endpoint readiness, lease and replay observations | Route to healthy capacity, pause planned work, and add bounded survivor capacity where allowed. Investigate application and ALB failures separately. |
| Rotation blocked or approaching expiry | Validated revision, expected identity and trusted chains, Pod readiness and fresh handshake results | Preserve the last usable revision when possible. Escalate expiry or blocked trust before submitting another rotation. |

Instrument controller reconcile errors and latency, operation phases, no-progress time, eligible capacity by role/AZ, provisioning attempt and suppression counts, TLS expiry, and rollout holds. Give operators links or IDs that can be correlated with Kubernetes events, provider logs and Java local metrics. Keep metrics labels bounded and use logs or per-operation observations for Pod identities. [Java diagnostics and telemetry](../research/java-serverless-operations.md#health-performance-and-diagnostics)

## Decisions to close before beta

| Decision | Evidence or owner input |
| --- | --- |
| Deployment and SLO baseline | Agree per-role throughput, serving floors and largest-AZ failure target. Specify Kubernetes versions, the EKS and GKE node families, the ingress implementation, and required warm and emergency capacity. |
| Strict warm signal | Select a cheap Java status or probe with explicit success, timeout, error and empty or insufficient sample. Define how a wholly cold fleet admits degraded traffic without opening the normal maintenance gate by accident. |
| GKE direct Pod drain | Confirm custom controller ownership, PDB, `preStop` and grace behavior with the target GKE Standard update and repair paths. Evaluate the [zonal workload alternatives](../research/multi-az-operator-design.md#when-to-own-pods-directly) if direct ownership cannot meet the required drain contract for the target. |
| Production Java TLS and identity | Choose a packageable provider, peer identity stable enough for verification, HTTPS behavior, cert-manager issuer integration, and store credential refresh. Test rotation with the same launcher and image that users will run. |
| GKE primary store and workload identity | Select an already qualified shell backend for the initial GKE deployment or implement and qualify a new one when native GCS is required. Verify compare-and-swap, listing consistency, durability, replay, slow or ambiguous outcomes, and actual credential refresh. |
| Blue/green compatibility | Identify what can certify mixed writes, reads, peer messages and safe rollback for each version pair. A floating or unqualified image pair cannot be promoted under this design. |
| Tenant boundary | Decide who can create instances, who can approve traffic shifts, which ServiceAccounts and Secrets can be referenced, and which sidecars and routes are admitted. Verify effective permissions before allowing untrusted namespace authors. |

The design is ready for implementation review against these contracts. The repository currently contains research and design documents. Implementation, image builds, and live cloud qualification are tracked as future delivery work. [Architecture and source baseline](README.md)
