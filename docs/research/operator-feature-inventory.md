# OpenSearch Serverless Operator feature inventory

The operator would deploy and operate the Java OpenSearch serverless shell on Kubernetes. Its distinguishing feature would be independent control of **indexing and search capacity in each availability zone**, including how that capacity changes during rollout, maintenance, and failure recovery.

This is a proposed feature set based on the [published Java branch and operator references](README.md#source-snapshots). The first release below assumes that operators need exact Pod selection for planned disruption. Direct Pod ownership fits that requirement. If group-level rollout sequencing is enough, zonal Deployments can provide much of the same feature set with native Pod replacement. The [multi-AZ design](multi-az-operator-design.md) describes both models. The choice of workload implementation stays open. Direct Pod control will live in a [reusable lifecycle package](pod-lifecycle-package.md).

## Proposed first release

| Feature | What users can do and observe |
| --- | --- |
| Install and reconcile | Install the controller and CRD, then declare a namespaced serverless instance. Its spec drives Pods, Services, configuration, and disruption budgets. Repeated reconciliation repairs managed resources and resumes interrupted operations. Install artifacts describe supported Kubernetes versions and required permissions. |
| Run a pinned Java image | Choose an image digest and runtime settings. Set JVM heap, CPU, memory, ephemeral storage, scheduling restrictions, and image pull references by pool. The image runs the Java shell entry point as non-root, mounts its work and config paths, and delivers termination signals to the JVM. The launcher and deployable image must be built and qualified. |
| Configure indexing and search capacity independently | Create `ingest` and `search` pools with separate resource profiles. Set an exact desired replica count and a minimum serving count for each required role and AZ. Expose intentionally omitted capacity separately from a scheduling shortfall. Enforce AZ placement with Node topology and report the zone the shell advertises. |
| Use dedicated nodes | Optionally place one OpenSearch Pod per node, including across blue/green revisions. Qualify different node profiles for indexing and search against actual allocatable resources and matching DaemonSet requests. Bound pending demand and pause replacements when nodes repeatedly arrive without a binding. Use platform-managed capacity on EKS with Karpenter or on GKE Standard. See the [dedicated-node design](dedicated-node-placement.md). |
| Optional sidecars per pool | Add containers such as a log shipper, OpenTelemetry Collector, or local proxy to indexing or search Pods. Configure image, resources, probes, and explicit shared mounts. Include sidecar resource requests in AZ surge calculations and version sidecar changes with the Pod template. |
| Expose role-specific endpoints | Provide stable internal indexing and search Services. Enable optional same-AZ client endpoint preference on supported clusters. Configure direct, reachable Pod transport addresses for Java peer forwarding. Restrict client ingress, peer transport, and access to the store according to the deployment's policy. |
| Bind a durable object store | Reference an existing S3-compatible endpoint, exclusive bucket, and credentials. Validate required settings and report failures without exposing credential contents. Use Pod-local storage for recoverable local state once fresh-Pod replay is proven. Preserve the bucket and its data when deleting or recreating the resource. A bucket change requires a separate migration or restore workflow. |
| Check startup, readiness, and membership | Use liveness for process health. Use startup and search readiness together with valid lease evidence for traffic admission. Verify a new Pod's advertised address and zone and test reachability from another Pod before treating it as a rollout successor. Report Pod readiness and Java membership independently so operators can see why a running Pod remains out of service. |
| Scale and rebalance by AZ | Scale a role up or down in a specified zone. Check the resulting serving floors before planned reductions. When moving capacity between AZs, verify the destination before reducing the source. Surface unschedulable capacity explicitly. |
| Replace Pods and roll changes safely | Stage changes to the pinned image, configuration, or referenced runtime material. Apply a per-role/AZ serving floor and a global surge or concurrency budget. Bring a successor up in the intended zone, verify eligibility, then retire old capacity. Support a canary wave and pause or resume between waves. If exact victim selection and per-Pod drain are release requirements, use direct Pod control. |
| Blue/green deployment | Build and verify a candidate fleet by role and AZ while the current revision serves. Offer restricted preview, explicit promotion, and a rollback window for verified compatible versions. Both revisions share the Java data plane in the initial design. See the [blue/green strategy](blue-green-deployment.md). |
| Drain and maintain | For a planned replacement, remove the chosen Pod from client traffic, allow search cache handoff where applicable, and give the JVM time for shutdown and writer publication. Apply a zonal PDB for eviction-based maintenance. Directly owned Pods can use an integer `minAvailable` PDB with suitable selectors. The operator checks its own rollout floors before planned actions. |
| Recover from failures | Resume replacement after a Pod or controller failure. Java applies lease expiry, ownership fencing, and WAL replay for lost writers. During an AZ outage, show which floors are unmet, stop planned disruption that would worsen the loss, and allow service and Java routing to use healthy survivors where configured. Qualify the required spare capacity for the target failure scenario. |
| Handle node maintenance | Observe Pod disruptions through the namespaced Pod watch, use Java shutdown for graceful evictions, and accept optional namespaced hints from a platform publisher. Hold planned changes during a capacity shortfall and limit concurrent search warmups during recovery. See [node maintenance and loss](node-disruption-recovery.md). |
| Integrate authentication and TLS | Accept provided Secrets for HTTP TLS and transport mTLS, with optional issuance through cert-manager. Rotate leaf keys and certificates through role/AZ-aware Pod replacement and support coordinated CA rollover with overlapping trust bundles. Verify fresh handshakes and preserve authorized access to administration endpoints. Limit initial access to a defined trust domain until authorization has been verified end to end. See the [TLS design](tls-certificate-rotation.md). |
| Report health and rollout state | Show observed generation, target and running image revisions, endpoint names, and desired, scheduled, ready, and lease-eligible counts by role and AZ. Report the exact blocker and phase during rollout, degraded placement, or recovery. Include recent Kubernetes events and link observations back to node or Pod identity. |
| Export operational diagnostics | Publish controller reconciliation and rollout metrics. Integrate Java lease, queue, capacity, store request, and inter-AZ transport metrics with the selected monitoring system. Report timestamped, bounded observations with known collection failures visible. |

The shell takes JVM settings and secure inputs through its bootstrap. `/_serverless/ready` covers started and search-readiness state, while `/_serverless/stats` provides a local lease signal. These are existing runtime inputs for the operator, and wiring them into admission requires a deployment test. Port checks alone cannot establish that a peer can reach a published transport address. [Java launch and signals](java-serverless-runtime.md) · [Readiness handler](https://github.com/huyz0/OpenSearch/blob/e71d42331a3ec82ec01109a5bb42d6a9a9162a5c/serverless/shell/src/main/java/org/opensearch/serverless/rest/ServerlessReadyHandler.java) · [Lease and traffic stats](https://github.com/huyz0/OpenSearch/blob/e71d42331a3ec82ec01109a5bb42d6a9a9162a5c/serverless/shell/src/main/java/org/opensearch/serverless/rest/StatsHandler.java) · [Kubernetes readiness gates](https://kubernetes.io/docs/concepts/workloads/pods/pod-condition/#enhanced-pod-readiness) · [PDBs for arbitrary workloads](https://kubernetes.io/docs/tasks/run-application/configure-pdb/#arbitrary-workloads-and-arbitrary-selectors)

## Sidecars and shutdown

Expose a pool-level `sidecarContainers` option. The OpenSearch operator renders the complete Pod template and validates container names, ports, and shared volumes. Prefer Kubernetes-native sidecars for containers that need to start before Java or remain running during Java shutdown. On supported clusters, render them as `initContainers` with `restartPolicy: Always`. A sidecar `startupProbe` can gate Java startup. A sidecar `readinessProbe` contributes to Pod readiness, so only gate serving on a sidecar's health when traffic or durability depends on it. The Pod grace period must cover Java handoff with any required proxy or helper still running. Both revisions of the Pod template need capacity in the target AZ during blue/green. [Kubernetes sidecar lifecycle and resource requests](https://kubernetes.io/docs/concepts/workloads/pods/sidecar-containers/)

## Follow-on features

| Feature | What needs to be established first |
| --- | --- |
| Independent autoscaling | Use separate signals and bounds for indexing and search. Java's `fleet.wanted_nodes` is a writer estimate from lease observations. Search needs its own measurements. Apply stabilization and per-AZ floors and have one owner for each replica target. Distinguish compute saturation from object-store slowdown. [Fleet estimate](https://github.com/huyz0/OpenSearch/blob/e71d42331a3ec82ec01109a5bb42d6a9a9162a5c/serverless/shell/src/main/java/org/opensearch/serverless/node/FleetPlacement.java) · [Kubernetes scale interface](https://kubernetes.io/docs/reference/kubernetes-api/autoscaling/horizontal-pod-autoscaler-v2/) |
| Bounded AZ failover and failback | Optionally grow specific surviving AZs within quotas, then restore the intended distribution after the failed zone returns. Qualify service capacity and cross-AZ costs on the surviving fleet. Decide whether failback concerns compute counts only or also writer placement. |
| Per-Pod writer drain and verified handoff | Before terminating a named writer, stop sending it new write work, wait for admitted writes and durable ownership release, and verify that peers can resume the affected work. The current shell's administrative drain is for search. Writer handover runs during JVM shutdown. Pre-delete writer drain and handoff confirmation need a Java contract. [Search drain](https://github.com/huyz0/OpenSearch/blob/e71d42331a3ec82ec01109a5bb42d6a9a9162a5c/serverless/shell/src/main/java/org/opensearch/serverless/warm/SearchDrain.java) · [Shutdown](https://github.com/huyz0/OpenSearch/blob/e71d42331a3ec82ec01109a5bb42d6a9a9162a5c/serverless/shell/src/main/java/org/opensearch/serverless/shell/ServerlessBootstrap.java) |
| Hard per-index AZ policy | Pin a writer's preferred or required zones, control reader locality per index, or move ownership back after failover. Pod placement, same-AZ writer takeover preference, and hot-reader affinity are available now. Hard per-index rules and fallback semantics would require Java routing and ownership changes. [Writer takeover](https://github.com/huyz0/OpenSearch/blob/e71d42331a3ec82ec01109a5bb42d6a9a9162a5c/serverless/shell/src/main/java/org/opensearch/serverless/node/FleetPlacement.java) · [Reader zone preference](https://github.com/huyz0/OpenSearch/blob/e71d42331a3ec82ec01109a5bb42d6a9a9162a5c/serverless/shell/src/main/java/org/opensearch/serverless/cluster/ZonePreference.java) |
| Backup and restore orchestration | Add on-demand and scheduled snapshots, retention, restore into a separate deployment, and recovery verification for defined objectives. A separate backup workflow needs to protect against loss or corruption of that store and qualify restore semantics. ## Checks to qualify the first release

- Apply a two-role configuration across three labelled AZs, including unequal replica targets. Verify actual placement, matching Java lease zones, and indexing and search through their Services.
- Fail first lease publication, misconfigure a peer address, and trigger a shared-store outage. Verify that the operator neither admits an unusable successor nor treats the outage as a reason to restart the fleet.
- Roll a single-Pod AZ with and without surge room. Verify the serving floor, show the blocked zone when capacity cannot be added, and recover safely from a controller restart during a wave.
- Delete an indexing Pod gracefully, then hard-stop a writer in a separate run. Distinguish handover from fenced replay, and record acknowledged writes, unknown outcomes, recovery time, and query coverage. Restore the fleet with fresh Pod-local paths on the same bucket.
- Exercise voluntary node eviction and an AZ outage during rollout. Verify intended pauses, surviving capacity, fallback, and eventual return to desired placement.
- Qualify blue/green with insufficient candidate capacity, mixed traffic during promotion, controller restart between Service changes, and rollback on a populated shared bucket.
- Exercise TLS leaf renewal and staged CA rollover with fresh handshakes and mixed old and new Pods, and verify that a bad certificate revision blocks replacement.
- Run startup, traffic admission, and writer shutdown with a dependent sidecar enabled. Verify that termination ordering preserves peer and store access through Java shutdown and that sidecar resource requests are included in the AZ surge budget.
- Verify dedicated-node placement across roles and revisions on EKS and GKE. Increase DaemonSet requests during a rollout and verify that a Pod that cannot fit does not continue to trigger new nodes after the operator withdraws it. See the [dedicated-node qualification cases](dedicated-node-placement.md#qualification-before-rollout).
- Delete the custom resource and recreate it against the same supplied store. Verify retention and test rollback on a populated bucket only for an image pair with proven format and transport compatibility.

The first-release feature list makes no live availability or recovery-time claim. These checks extend the branch's [pilot readiness evidence](https://github.com/huyz0/OpenSearch/blob/e71d42331a3ec82ec01109a5bb42d6a9a9162a5c/serverless/pilot-readiness.md) and the [multi-AZ test cases](multi-az-operator-design.md#verification-that-distinguishes-the-designs). This research was based on source and documentation. No operator code or Kubernetes deployment was changed.
