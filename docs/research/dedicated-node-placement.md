# Dedicated nodes for indexing and search

Offer an optional placement mode with at most one Java OpenSearch Pod per node. Indexing (`ingest`) and search each define a Pod resource profile and a dedicated node profile. Both keep the role and AZ counts in the [multi-AZ design](multi-az-operator-design.md). On EKS, use platform-managed Karpenter NodePools. On GKE Standard, start with dedicated managed node pools and the native cluster autoscaler. The OpenSearch operator controls when workload Pods become eligible for scheduling and when an existing Pod may retire.

## Placement and ownership

| Owner | Responsibilities |
| --- | --- |
| Platform | Publish a label and permanent `NoSchedule` taint for each capacity profile, restrict eligible machine shapes and AZs, set bootstrap and system reservations, and configure autoscaling bounds. Allow required platform DaemonSets on the dedicated nodes. Keep the provisioner and operator on their own system capacity. |
| OpenSearch operator | Render matching required node affinity and the exact profile toleration, plus the required AZ using `topology.kubernetes.io/zone`. Use hard Pod anti-affinity on `kubernetes.io/hostname` against a common OpenSearch label that applies to both roles and every blue/green revision. The default scope is one OpenSearch instance. A shared fleet label and explicit namespace selection can extend the scope to multiple instances. |
| Kubernetes scheduler and provisioner | Bind Pods through the normal scheduler and provision nodes through the configured platform. The operator can observe capacity and events with read-only access. |

A Pod may include Java plus sidecars and init containers. The dedicated-node taint keeps workloads without a matching toleration off the pool. Platform policy must restrict broad tolerations if dedicated capacity must exclude other workloads. Use eligible fallback machine types in the same AZ when they satisfy the same profile. A shortage in an AZ leaves that AZ's target pending. [Kubernetes affinity and anti-affinity](https://kubernetes.io/docs/concepts/scheduling-eviction/assign-pod-node/) · [Taints and tolerations](https://kubernetes.io/docs/concepts/scheduling-eviction/taint-and-toleration/)

Keep the profiles independent. Size indexing for ingest throughput, JVM and native memory, and local WAL work or replay where configured. Size search for query concurrency, JVM and native memory, warmed caches, and local cache I/O. The Pod profile specifies requests, limits, heap and local storage. The capacity profile records the qualified machine shapes, node image and bootstrap settings, disk and Pod slots, matching DaemonSets, and the required headroom. Choose both from load and rollout measurements. Tie scheduling eligibility to a capacity profile revision so an old, incompatible node cannot match a Pod that needs the new profile. [Java runtime paths and configuration](java-serverless-runtime.md)

## Fit calculation

For each eligible machine shape and AZ, qualify the combination of node image, kubelet configuration, disk, CNI and Pod slot limits against registered nodes. Record the lowest observed `Node.status.allocatable` for CPU, memory, ephemeral storage and Pod slots across representative fresh nodes. Set explicit headroom per dimension using observed variation and expected platform changes. Kubelet and system reservations already reflected in allocatable are accounted for at that point. Treat the qualification as evidence for a particular configuration, with a timestamp and a revision. [Kubernetes Node Allocatable](https://kubernetes.io/docs/tasks/administer-cluster/reserve-compute-resources/) · [GKE node sizing](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/plan-node-sizes)

```text
effective OpenSearch Pod requests
+ maximum expected requests of matching DaemonSets and other required node Pods
+ headroom
<= minimum observed allocatable, in each resource dimension
```

Use the admitted Pod spec for the OpenSearch request calculation so admission-injected sidecars, init-container scheduling rules, RuntimeClass overhead and request defaults are all visible. Count one slot for the OpenSearch Pod and one per matching node Pod. Count expected DaemonSets even if they have yet to land on a new node. When DaemonSet generations may overlap, model the largest expected footprint for each node. Use the larger generation's request per resource for replacement without overlap, and sum the requests if both versions can run on that node during the update. Include already assigned system Pods when checking an individual node, counting each request once. Also validate hard scheduling constraints such as host ports, taints, affinity and volume topology. [Kubernetes sidecar resource accounting](https://kubernetes.io/docs/concepts/workloads/pods/sidecar-containers/#resource-sharing-within-containers) · [Pod overhead](https://kubernetes.io/docs/concepts/scheduling-eviction/pod-overhead/)

For example, an OpenSearch Pod asks for `6800m` CPU and `26Gi` of memory including its sidecars. The node registers `7800m` and `30Gi`. DaemonSets ask for `500m` and `2Gi`, leaving `500m` and `2Gi` for headroom. If a DaemonSet update takes the total to `1100m` and `5Gi`, Pod and DaemonSet requests alone exceed the node by `100m` and `1Gi`. Pause the new work and qualify a larger shape or change the platform workload budget. Check CPU and memory usage as well as requests when choosing headroom. Under-requested agents can still create memory pressure or CPU contention even when the scheduler accepts the Pod.

## Handling DaemonSet and node changes

1. Invalidate the affected qualification when a matching DaemonSet changes resources or placement, when admission changes the OpenSearch Pod footprint, or when node image, bootstrap, CNI, Pod slots or disk change. Check live nodes as well for a newly introduced agent or unexpected bootstrap taint.
2. For a planned platform upgrade, qualify the incoming DaemonSet footprint before broad rollout. Where the agents and platform permit, stage the node and agent change on a bounded canary pool in the affected AZ. Check actual allocatable, scheduler fit, required agent readiness, Pod pressure and Java serving health. Protect existing nodes with the sizing budget or migrate serving workloads onto qualified capacity before expanding an agent change that exceeds it.
3. Gate new Pod placement against the current qualification. Use a small canary wave after a profile change and observe both binding and OpenSearch readiness before expanding. A higher-footprint Pod may require a different machine shape. Capacity profile changes do not change JVM heap or silently reduce requests on a running Pod.

The headroom figure is a qualification threshold. Karpenter and the Kubernetes scheduler do not reserve it from unrelated workloads. Enforce it by restricting what can land in the node pool and exposing only qualified shapes and configuration. For stronger isolation, evaluate platform policy and kubelet resource configuration against the same fit check.

## Limit the effect of provisioning failures

1. **Admit a bounded wave.** When using direct Pod control, create a Pod with the operator's scheduling gate where supported. Inspect the admitted Pod, then release eligible Pods within per-role/AZ and total pending-demand budgets. Start qualification with one provisionable candidate at a time per role/AZ and a small explicit global budget. Pod scheduling gates must be present at creation and can only be removed. A Pod that stays gated does not enter normal scheduling or trigger demand in the inspected Karpenter path. [Kubernetes scheduling gates](https://kubernetes.io/docs/concepts/scheduling-eviction/pod-scheduling-readiness/) · [Karpenter Pod eligibility](karpenter-scheduling-research.md#code-path-on-aws)
2. **Track whether new capacity helps.** For each wave, track pending age, launched and registered capacity, and successful bindings by role/AZ. Give nodes a startup window based on observed join time. Set a launch-without-binding threshold and a separate no-progress timeout for cases with no launches or failed registration. Surface Pod scheduler events, expected and actual resources, and the impacted role and zone. Correlate capacity conservatively by profile, zone and time, with nomination events where available. Keep workload readiness failures separate once a Pod has a node.
3. **Withdraw the scheduling demand on repeated failure.** Persist the blocked state before taking action, hold other candidates, and re-read an affected managed Pod from the API. Delete the specific owned, still-unbound Pod with UID and resource-version preconditions. If it bound in the meantime, observe the bound Pod through the normal lifecycle. Wait for the withdrawn Pod to disappear and preserve the blocked state on controller restart. Keep serving Pods and delay their retirement. A rollout pause alone leaves an unschedulable Pod visible to the autoscaler, and a scheduling gate cannot be added back. Keep desired replica counts visible in status. Resume on a relevant capacity or configuration change, or allow a limited retry with backoff for transient failures. [Kubernetes deletion preconditions](https://kubernetes.io/docs/reference/kubernetes-api/definitions/delete-options-v1-meta/)
4. **Set the outer resource limits.** A single pending Pod can cause several launches over time. Configure NodePool CPU and memory limits, node count where supported by the installed version and mode, and suitable provider quotas. Karpenter limit checks are eventually consistent, so allow for launch races and nodes already in flight. The operator leaves Node and NodeClaim cleanup with the provisioner. If workload-driven launches are unacceptable during a rollout, use bounded, pre-provisioned capacity. [Karpenter NodePool limits](https://karpenter.sh/docs/concepts/nodepools/#speclimits)

Use the same budget for scale-out, replacements, TLS rotations and blue/green candidates. Each dedicated candidate needs its own node while its predecessor is still running. Count simultaneous blue and green nodes by role and AZ, plus any separately allowed infrastructure replacements. Check the affected role and AZ's serving floor before each planned retirement. The reusable [Pod lifecycle package](pod-lifecycle-package.md) can expose generic scheduling gates and conditional withdrawal of an unbound Pod. The OpenSearch controller owns role/AZ admission, capacity qualification and application readiness. [Blue/green capacity and promotion](blue-green-deployment.md)

Use separate zonal pools where the platform needs per-AZ infrastructure limits. ## Keep warm Pods through consolidation

Run the [warm spare replicas](node-disruption-recovery.md#configure-warm-spare-capacity-by-role-and-az) as ordinary serving Pods. Set `WhenEmpty` on the dedicated Karpenter NodePools for both roles. Karpenter can reclaim a node after its workload Pod leaves. A running OpenSearch Pod with normal disruption cost keeps its node out of empty-node consolidation, even when the Pod is lightly loaded. Keep the default disruption cost for these Pods. The hostname rule keeps each warm Pod on its own host. [Karpenter consolidation and disruption cost](https://karpenter.sh/docs/concepts/disruption/)

For example, a platform-owned NodePool can use the following disruption settings. The delay is illustrative and controls empty-node cleanup. Apply an explicit drift budget separately from the consolidation policy.

```yaml
spec:
  disruption:
    consolidationPolicy: WhenEmpty
    consolidateAfter: 10m
    budgets:
      - nodes: "1"
        reasons: [Drifted]
```

Drift, expiration, repair and infrastructure interruptions remain possible. Coordinate drift budgets across pools and account for nodes created together when choosing expiration settings. The OpenSearch operator needs only its workload permissions. The platform owns NodePool settings and applies the interruption policy. [Karpenter disruption controls](https://karpenter.sh/docs/concepts/disruption/)

If a separate requirement calls for an empty host ready for the next Pod, reserve it separately through platform capacity settings. On supported Karpenter versions a static NodePool maintains `spec.replicas` without workload demand and its nodes are excluded from consolidation. Size any empty standby capacity by role and AZ. It reduces provisioning delay while a running search Pod can serve immediately. [Karpenter static pools](https://karpenter.sh/docs/concepts/nodepools/#specreplicas)

## Keep warm Pods on GKE Standard

The platform sets autoscaling minimums on dedicated managed node pools. With one Pod per node, set each role's **per-zone minimum** to the total number of search or indexing Pods that should stay warm there. For example, a steady target of three search Pods and two indexing Pods per AZ maps to `--min-nodes=3` on the search pool and `--min-nodes=2` on the indexing pool. The flags apply uniformly to every zone in each pool. Use separate zonal pools when the floors must differ by AZ. GKE's `--total-min-nodes` only maintains an aggregate count across zones. Keep max size and quota available for planned surge, and provision the baseline through the initial pool size or normal Pod demand. Raising a minimum above current size can leave it below the minimum until demand arrives or the pool is resized. [GKE autoscaling limits and behavior](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/cluster-autoscaler#autoscaling-limits)

The operator maintains the [per-role, per-AZ replica targets](node-disruption-recovery.md#configure-warm-spare-capacity-by-role-and-az), hard zone placement, and one OpenSearch Pod per host. When there is nowhere eligible to move a Pod, GKE cluster autoscaler leaves its node alone. A node minimum protects the count. The following **Pod annotation** additionally keeps GKE Cluster Autoscaler from selecting a node for scale-down while it hosts a protected Pod, even if another node could accept that Pod.

```yaml
metadata:
  annotations:
    cluster-autoscaler.kubernetes.io/safe-to-evict: "false"
```

Render this annotation into every serving search or indexing Pod that should retain its cache or placement, including the replicas that provide spare capacity. The operator can set it when it creates the Pod with its ordinary namespaced permission. The platform manages the node pools. Once the operator intentionally retires a Pod, the autoscaler can reclaim excess empty nodes above the pool minimum. If the platform holds a higher fixed node minimum, it also needs to lower that minimum before those nodes are returned. [GKE Pod scale-down blockers](https://docs.cloud.google.com/kubernetes-engine/docs/troubleshooting/cluster-autoscaler-scale-down)

Treat the annotation as Pod lifetime policy. Put it in the initial Pod create request and retain it through readiness changes, reserve use, and operator-managed retirement. Removing it from a live Pod can make the node eligible while a replacement is still warming. Reapplying it successfully only confirms that Kubernetes stored the change. GKE documents a scale-down eligibility check and gives no cancellation guarantee for a drain in progress. In upstream Cluster Autoscaler, the drainability check uses a snapshot and precedes asynchronous eviction requests. Kubernetes evaluates PDBs at eviction. The autoscaler annotation itself is not an eviction admission rule. For a change in protection policy, use a controlled Pod replacement wave. Let the old protected Pod drain and disappear with its annotation still set. [GKE scale-down reasons](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/cluster-autoscaler-visibility) · [Upstream scale-down actuation](https://github.com/kubernetes-sigs/cluster-autoscaler/blob/7b528926d793584d588e0ad5bfab58ff499328ae/pkg/core/scaledown/actuation/actuator.go#L391-L424) · [Kubernetes eviction](https://kubernetes.io/docs/concepts/scheduling-eviction/api-eviction/)

Keep the role/AZ PDB for voluntary drain availability. A PDB set to the serving floor can allow eviction of a healthy spare, while the Pod annotation protects it from autoscaler scale-down. GKE upgrades, auto-repairs, and infrastructure failures are governed by their own maintenance and recovery paths. In a qualification run, keep the pool above its minimum and provide another eligible empty host in the AZ. Inspect GKE's scale-down reasons for `no.scale.down.node.pod.not.safe.to.evict.annotation` and check that an excess node becomes eligible after intentional Pod retirement. A direct-managed Pod can also encounter the unrecognized-controller blocker. Exercise the production ownership and affinity for both roles, and isolate the annotation in a recognized-controller fixture if another blocker masks it. [GKE scale-down diagnostics](https://docs.cloud.google.com/kubernetes-engine/docs/troubleshooting/cluster-autoscaler-scale-down) · [Node disruption recovery](node-disruption-recovery.md)

## Qualification before rollout

Test cold launches and placement for both roles in each target AZ, including a second Pod that must land on another host, and repeat during a blue/green overlap. Exercise a DaemonSet request increase and surge, an admission-injected sidecar, a capacity forecast above registered allocatable, a Pod-slot shortfall, and a startup taint that fails to clear. Confirm that the operator reports the first failed condition, bounds new demand, withdraws an unbound Pod safely, and preserves live serving capacity. Restart the operator mid-pause and race withdrawal with binding. For each platform, record how many nodes can still arrive after withdrawal because they were already in flight. Run an AZ shortage test to confirm that the incomplete zone target is visible and no Pod is placed across the zone boundary.

On EKS, leave an eligible warm spare on a lightly loaded node for longer than `consolidateAfter` and verify Karpenter keeps it. Reduce the desired replica count within the serving floor and verify the newly empty node becomes eligible for cleanup. Repeat with AMI drift to verify it follows the separate node disruption budget.
