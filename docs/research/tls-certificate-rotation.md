# TLS certificate setup and rotation

Support both **user-provided Kubernetes TLS Secrets** and **optional issuance through cert-manager**. Use the same operator rollout for either source. The operator observes a complete certificate and key pair, validates it, and makes new Pods serve it before retiring old capacity. Coordinated CA rollover is a separate workflow because it changes what peers and clients trust.

## Reference behavior and the Java boundary

The upstream OpenSearch operator handles HTTP and transport TLS separately. It supports generated certificates and referenced Secrets, including separate CA material and per-node transport certificates. Its Security plugin integration can hot-reload renewed certificates on supported versions. For generated certificates when hot reload is disabled, its renewal marker can trigger a rolling restart. Its migration guide calls out CA replacement separately from leaf renewal. Our Java shell exposes a `SecureSettingsFactory` integration. Its `tlsTest` fixture exercises encrypted peer transport, mutual TLS, and rejection of a peer that presents no certificate. That fixture returns no HTTP TLS provider. The shell bootstrap forwards an allowlist of JVM setting prefixes and does not consume stock `opensearch.yml`. Packaging a supported provider and proving its rollout behavior are prerequisites. The stock Security plugin's file watcher and reload endpoints require separate qualification on the selected shell image. The fixture's client engine does not configure endpoint identification, and its embedded certificate and password are test data. It is not a production identity-verifying provider. A real provider must establish and test the peer identity used for the advertised address; a secure transport setting or a successful TLS handshake alone does not establish that property.

An experimental operator-owned peer provider now builds into the shell bundle and enforces endpoint identification for outgoing connections. Local integration tests exercised a forwarded write and rejected a wrong advertised IP identity and an untrusted root. It requires client certificates but does not authorize their individual identities, and its HTTP, rotation, Kubernetes and production security gates remain open. [Build and test details](../implementation/java-runtime-build.md#experimental-peer-tls-provider)

A second experimental provider supplies HTTPS with separate certificate material and optional client certificate verification. Local Java tests exercise HTTPS alongside the peer provider, including missing and untrusted client certificates. It is not an authorization provider, and ingress, certificate rotation and workload health-probe wiring still require integration and qualification. [Runtime details](../implementation/java-runtime-build.md#experimental-peer-tls-provider)

An experimental Java overlay can publish a DNS hostname in the peer lease instead of the bound IP. A local forwarded-write test verifies that name against a DNS-only certificate. A Kubernetes integration still needs to supply and verify a unique Pod DNS record, including before readiness and across deletion and name reuse. [DNS overlay evidence](../implementation/java-runtime-build.md#experimental-peer-tls-provider)

The independent `internal/tlsconfig.ValidateRollover` preflight checks supplied leaf chains against the overlap bundle, and checks leaves marked for retention against the final bundle, for each declared identity and client/server usage at both ends of a caller-selected validity window. Its caller must provide the complete active and rollback inventory. It neither observes actual fleet convergence nor performs a handshake, and is not yet connected to a controller operation.

## Certificate sources and TLS boundaries

| Boundary | Managed inputs and behavior |
| --- | --- |
| Client to Ingress or Gateway | The Ingress or Gateway uses its own client-facing TLS Secret. Its controller serves and renews that certificate according to the selected integration. Frontend TLS management is independent of Pod certificate rollout. |
| Direct HTTP or Ingress to Pod HTTPS | Reference an HTTP TLS certificate and key plus the trust material needed by clients or an HTTPS upstream. Verify the DNS name or backend identity clients actually use. Use Pod HTTP TLS when clients connect directly over HTTPS or the ingress is configured to use TLS to the Pod. |
| Java peer transport | Supply the node identity, private key, and peer CA bundle. Qualify mutual TLS in both directions and verify the identity the runtime expects for the address published in the lease. For direct Pods the address may be an ephemeral Pod IP, or the provider may support an identity based on a stable DNS name or certificate identity. Issuance and verification must agree on that contract before promising per-Pod identities. |
| Java to the object store | The S3 endpoint's TLS trust and credentials stay independently configured. Rotating a node identity must preserve connectivity to the store. |

[TLS Secret format](https://kubernetes.io/docs/concepts/configuration/secret/#tls-secrets) · [Java deployment and networking](java-serverless-runtime.md#membership-and-network) · [Peer address handling](https://github.com/huyz0/OpenSearch/blob/e71d42331a3ec82ec01109a5bb42d6a9a9162a5c/serverless/shell/src/main/java/org/opensearch/serverless/transport/ShardRouter.java)

For user-provided material, reference same-namespace `kubernetes.io/tls` Secrets with `tls.crt` and `tls.key`. Reference a distinct trust bundle so CA overlap can be staged independently of leaf replacement. For managed issuance, allow a reference to an existing cert-manager `Issuer` or `ClusterIssuer`, request the required certificate identities and usages, and choose `privateKey.rotationPolicy: Always` when both the key and certificate should renew. Keep issuer signing keys with the issuer. Use Secret references for private keys and report only public fingerprints, expiry, and rotation progress. [Kubernetes TLS Secrets](https://kubernetes.io/docs/concepts/configuration/secret/#tls-secrets) · [cert-manager Certificate resources](https://cert-manager.io/docs/usage/certificate/)

## Leaf certificate and key rotation

1. **Observe and validate.** Reconcile when a referenced Secret changes or cert-manager issues a new pair. Validate PEM format for the provider, key-to-certificate match, trust chain, validity, and required identities and usages. Report a rejected candidate and preserve the last usable revision while it remains valid.
2. **Pin and stage.** Record the validated certificate and trust revision. Ensure a new Pod receives that exact version, for example through a versioned Secret reference. This matters when user-provided or cert-manager Secrets can change during a rollout. Reuse the existing per-role and per-AZ surge and serving floors.
3. **Verify and advance.** Check a fresh TLS handshake using normal trust and identity verification, then verify the new Pod's lease and application traffic. Test peer transport in both directions during a mixed-certificate wave. Check through the actual HTTPS ingress or direct client path where applicable. Kubelet HTTPS probes skip certificate verification, so Pod readiness alone cannot prove rotation. [Kubernetes probe behavior](https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/)
4. **Retire the old Pods.** Drain and replace them in the configured order. Record any blocked AZ, the certificate revisions served, and expiry. If blue stays as a rollback target, keep its TLS identity usable for the rollback window or report the time at which rollback ceases to be viable.

Use a controlled Pod rollout as the first rotation mechanism. Add a provider-specific hot reload mode after proving that fresh handshakes serve the new leaf and apply the intended trust bundle without a JVM restart. Use a mounted Secret directory when relying on in-place Kubernetes updates. Secret updates propagate eventually, and mounts using `subPath` do not pick up these updates. [Kubernetes Secret volume updates](https://kubernetes.io/docs/concepts/configuration/secret/#using-secrets-as-files-from-a-pod) · [Blue/green rollback](blue-green-deployment.md#promotion-and-rollback)

## CA rollover

1. Publish a trust bundle that accepts **both old and new CAs**. Roll or reload it on the peer fleet and on clients or gateways that validate the Pod certificate. Verify that both chains can be trusted before placing new-CA leaf certificates into service.
2. Issue new leaf certificates and keys under the new CA. Roll them out by role and AZ. Throughout the overlap, prove old and new peer Pods can authenticate each other and serve requests.
3. After all peers and validating clients have migrated and rollback revisions no longer need the old CA, remove it from the trust bundle in a second controlled rollout. Verify that new connections using the old chain are rejected.

Treat the CA bundle as a deliberate operator or platform input. cert-manager's CA issuer can issue leaves, but changing its signing Secret does not automatically reissue existing leaf certificates. Coordinate reissuance with the trust rollout. [cert-manager CA issuer limitations](https://cert-manager.io/docs/configuration/ca/) · [trust-manager CA rotation guidance](https://cert-manager.io/docs/trust/trust-manager/)

Qualify BYO and managed issuance with a valid rotation, mismatched key and certificate input, slow or failed issuance, a blocked AZ surge, and a CA rollover with both old and new peers. Check HTTP and native transport separately. Test traffic and acknowledged writes while the writer Pods roll, including when a proxy sidecar must stay available through JVM shutdown. This is a proposed operator feature. No TLS provider or rotation was deployed for this study.

## Development snapshot primitive

`internal/tlsconfig` now contains a two-step Secret snapshot primitive. Planning reads exact source Secret UIDs and resource versions, validates the certificate/key pair, trust chain, required identities and usages, and a requested future validity window. Its intent contains only source identities and hashes of public certificate and trust material. After a caller persists that intent, execution creates an immutable owned Secret or recovers a matching existing one. If a source changes before creation, the snapshot is held; if it changes after creation, a matching snapshot can still be recovered. Private keys are not included in intent or status.

The development peer-TLS controller uses this primitive to stage an initial immutable snapshot from user-provided source Secrets and mounts it into Pods. It does not yet advance the baseline or perform certificate rotation. The caller must authorize source Secrets and protect snapshot ownership and names through namespace policy. An immutable Secret can be deleted and recreated under the same name, and Kubernetes volumes refer to names rather than UIDs; admission and workload identity controls remain necessary. Issuer integration, overlap rollouts, expiry recovery and safe cleanup remain open work.

The same package provides a fresh-connection HTTPS probe that checks the expected server identity and trust and can present a client certificate. Its result records the observed public leaf fingerprint and HTTP status; callers must separately decide which application response and client-auth policy are acceptable. Local Go TLS tests exercise old/new CA overlap, wrong identity, missing client certificates, and rejection after removing the old CA. They do not establish Java HTTP or peer TLS behavior.
