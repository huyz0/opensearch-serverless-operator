# Blue/green deployment for OpenSearch Serverless

Provide blue/green as an explicit rollout strategy alongside rolling replacement. The operator would keep the active revision serving while it creates a candidate revision with its own indexing and search Pods in each required AZ. Users could verify the candidate through restricted preview endpoints, approve promotion, and retain the previous revision for a rollback window.

## First variant to qualify

Use **shared-store blue/green** for an image pair verified to coexist. Both revisions bind the same bucket and participate in one Java deployment. Active and preview Services separate where clients enter the fleet. Java resolves peers through the shared lease registry. A preview request accepted by green can execute on blue, and blue can use green before promotion. A preview endpoint can restrict direct writes, but it cannot keep a green writer from joining the live data plane. Report this property in the rollout status and qualify the mixed-revision period from the moment green starts. Full isolation is a distinct capability. Runtime cohort controls would be needed to constrain peer routing and writer participation within a shared bucket. Separate buckets isolate membership and data, and would require a data-copy or replication protocol, a write fence at cutover, and a way to reconcile new writes before failback. The current branch does not supply that isolated cutover contract.

## Promotion and rollback

The selector-switch sequence assumes a stable ingress or Gateway proxy. Direct ALB IP targets need separate per-fleet target groups and health validation before a listener switch. See the [direct ALB design](../design/traffic-and-security.md#direct-alb-traffic-switches).

1. **Stage.** Record the active and candidate revisions. Start candidate pools within per-role and per-AZ quotas. A full candidate can approximately double steady-state Pod capacity while the previous revision is retained. Count sidecar resources in both revisions and use the intended sidecar image and configuration as part of each revision's template. If a required zone cannot fit candidate capacity, keep the active traffic assignment and report the shortfall.
2. **Qualify.** Check candidate image, placement, readiness, lease, transport, and role-specific client traffic. Run compatible read and write checks against the intended shared-store topology. A restricted preview check should distinguish the revision that accepted the request from the revision that executed it when making coverage claims.
3. **Promote.** Require explicit approval initially. Switch stable indexing and search endpoints to the candidate revision and record each switch. Two Kubernetes Service updates are independent, and endpoint propagation and existing connections can keep traffic on the previous revision temporarily. The design must tolerate mixed traffic during promotion and resume if the operator restarts after the first Service switches.
4. **Observe, roll back, or retire.** Keep the previous revision until the rollback window closes and remaining client traffic has drained. Switch back only if the previous image can still safely use the data and log formats the candidate wrote. Reverting client routing does not reverse storage mutations. Once the revision is retired, use ordinary recovery or rollout rather than promising an instant switchback.

The [Pod lifecycle package](pod-lifecycle-package.md) can create and retire either revision's Pods. The OpenSearch operator owns approval, active and preview Services, status, and validation. Argo Rollouts provides a reference for active and preview Services, pre- and post-promotion checks, and delaying old replica removal while traffic routing converges. [Argo Rollouts blue/green](https://argo-rollouts.readthedocs.io/en/stable/features/bluegreen/) · [Kubernetes EndpointSlices](https://kubernetes.io/docs/concepts/services-networking/endpoint-slices/)

Qualify promotion with a missing candidate AZ, a bad candidate image, live requests during a partial Service switch, a controller restart between Service changes, and rollback after writes on the promoted revision. Use a disposable shared object store and a compatible image pair. No blue/green deployment has been run for this study.
