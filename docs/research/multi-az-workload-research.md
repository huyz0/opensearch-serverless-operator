# StatefulSet AZ skew and PostgreSQL operator references

The relevant rollout property is how many **serving Pods of each role** remain in each availability zone. Scheduler spread constraints act when a Pod is placed. A workload controller decides what to delete, and the application decides when its replacement can serve. These decisions can preserve a fleet-wide replica count while leaving one zone with no serving Pods.

## Where StatefulSets lose zonal availability

| Mechanism | Consequence |
| --- | --- |
| StatefulSet `RollingUpdate` | Replaces Pods by ordinal, highest first. The same ordinal is recreated after the old Pod is deleted. It has no Deployment-style surge slot to make a new Pod available in that zone first. The update budget and partition are expressed in Pods and ordinals. [StatefulSet controller](https://kubernetes.io/docs/concepts/workloads/controllers/statefulset/#update-strategies) · [Kubernetes v1.35 implementation](https://github.com/kubernetes/kubernetes/blob/v1.35.0/pkg/controller/statefulset/stateful_set_control.go) |
| OpenSearch reference `OnDelete` | The upstream operator actually sets `Parallel` pod management and `OnDelete`. Its restart reconciler collects candidates across pools, orders by non-manager first, StatefulSet name, then descending ordinal, runs classic safety checks, and deletes a Pod for the StatefulSet to replace. The selection lacks an AZ ready-replica floor. Passing `topologySpreadConstraints` through the builder only constrains placement of the replacement. [Builder](https://github.com/opensearch-project/opensearch-k8s-operator/blob/b0be10474334e676c6044e7943322685af2e2d34/opensearch-operator/pkg/builders/cluster.go#L777) · [Restart selection](https://github.com/opensearch-project/opensearch-k8s-operator/blob/b0be10474334e676c6044e7943322685af2e2d34/opensearch-operator/pkg/reconcilers/rollingRestart.go#L178) · [Pod deletion](https://github.com/opensearch-project/opensearch-k8s-operator/blob/b0be10474334e676c6044e7943322685af2e2d34/opensearch-operator/pkg/reconcilers/rollingRestart.go#L370) |
| Soft or hard spread | `ScheduleAnyway` scores candidate nodes, so the new Pod can move to a surviving zone if the original zone has no room. `DoNotSchedule` can leave the replacement pending when the only permissible zone lacks capacity. With `minDomains`, a shortfall in eligible domains can set the skew baseline to zero, preventing additional replicas in zones already at `maxSkew`. Removal and readiness transitions can violate the desired distribution after scheduling. [Topology spread rules](https://kubernetes.io/docs/concepts/scheduling-eviction/topology-spread-constraints/) |
| Zonal volumes | A replacement using an existing zonal PV must fit that PV's node affinity. `WaitForFirstConsumer` helps choose a topology for initial provisioning. The existing volume's topology still applies on subsequent replacement. Omitting per-Pod PVCs removes this constraint for the Java shell if fresh local paths pass recovery tests. [Storage Class binding modes](https://kubernetes.io/docs/concepts/storage/storage-classes/#volume-binding-mode) · [PersistentVolume node affinity](https://kubernetes.io/docs/concepts/storage/persistent-volumes/#node-affinity) |
| Disruption budget | A PDB governs eviction through the eviction API. It can help during a node drain and cannot make a normal StatefulSet or Deployment rolling update respect a zonal floor. Direct Pod deletion also bypasses the PDB. [Pod disruptions](https://kubernetes.io/docs/concepts/workloads/pods/disruptions/#pod-disruption-budgets) |

A StatefulSet's identity can be valuable with per-instance storage. The problem for this operator is losing capacity in the zone before the replacement joins, especially with one Pod per role per zone. Keeping a single-replica StatefulSet per AZ would pin the intended placement and still replace that replica by deletion first.

## Why a single Deployment still has a gap

A Deployment can surge. `maxUnavailable: 0` protects the Deployment-wide available count during its rollout. The Deployment adjusts ReplicaSet counts and the old ReplicaSet selects its own Pods for scale-down. These steps do not consider a minimum for each AZ. Pod deletion cost is a preferential input to old-ReplicaSet selection. `matchLabelKeys: [pod-template-hash]` spreads each revision independently and cannot preserve a total availability floor across revisions. A selector common to both revisions also only constrains placement. It cannot control which Pod is removed afterwards. [Deployment rollout source](https://github.com/kubernetes/kubernetes/blob/v1.35.0/pkg/controller/deployment/rolling.go) · [ReplicaSet scale-down](https://kubernetes.io/docs/concepts/workloads/controllers/replicaset/#scaling-a-replicaset) · [Topology spread and revisions](https://kubernetes.io/docs/concepts/scheduling-eviction/topology-spread-constraints/)

| Count example | AZ A | AZ B | AZ C | Interpretation |
| --- | ---: | ---: | ---: | --- |
| Start | 1 | 1 | 1 | One serving Pod per zone for a single role. |
| StatefulSet deletes the old Pod in B | 1 | 0 | 1 | B has an immediate serving gap. If B cannot fit the replacement, a soft constraint can allow it to go to A. A strict constraint or zonal PV can leave it pending. |
| Single Deployment surges a new Pod in A | 2 | 1 | 1 | With a shared selector, placing the new Pod in A still fits `maxSkew: 1` at this point. |
| Single Deployment removes the old Pod in B | 2 | 0 | 1 | Three Pods remain available across the Deployment. There is no serving Pod in B. |
| Zonal Deployment surges in B, then removes an old Pod in B | 1 | 1 → 2 → 1 | 1 | The replacement uses capacity in B. With no surge room or no available replacement, the planned rollout waits. |

The columns count available Pods and assume the illustrated newly placed Pod has become available. The scheduler counts matching placed Pods, including Pods that have yet to become available. The examples describe possible sequences. They do not predict which old Pod a real ReplicaSet will select on any given cluster. The count model reproduced the two skew counterexamples and checked 105 single-zone handovers across sample three-zone replica targets. No Kubernetes cluster was run.

## PostgreSQL operator comparison

| Reference | How it manages instances | What transfers to the Java shell |
| --- | --- | --- |
| CloudNativePG | The Cluster controller owns individual PostgreSQL Pods and PVCs. It builds Pods with affinity and spread constraints, checks the instance and its PVCs, and reconciles absent instances. The rollout code uses application status, updates replicas before the primary, and supports primary restart or switchover. Where it deletes a Pod to update the image, the instance can come back on the same storage. [Custom controller](https://cloudnative-pg.io/docs/current/controller/) · [Pod creation](https://github.com/cloudnative-pg/cloudnative-pg/blob/e9eec0d3b49adb088f6fbcfa024d4ea288105c6e/internal/controller/cluster_create.go#L1500) · [Topology in Pod specs](https://github.com/cloudnative-pg/cloudnative-pg/blob/e9eec0d3b49adb088f6fbcfa024d4ea288105c6e/pkg/specs/pods.go#L214) · [Rollout logic](https://github.com/cloudnative-pg/cloudnative-pg/blob/e9eec0d3b49adb088f6fbcfa024d4ea288105c6e/internal/controller/cluster_upgrade.go#L54) |
| Crunchy Postgres Operator | Reconciles a zero-or-one-replica `OnDelete` StatefulSet per instance. Its instance sets expose affinity and spread constraints and add soft hostname and AZ spreading by default. The rollout reconciler checks application availability, limits planned unavailability across the cluster, and selects an instance for recreation. A primary can switch over via Patroni before replacement. [Per-instance StatefulSet](https://github.com/CrunchyData/postgres-operator/blob/0478c1dea748e6bc4cc382aba1210aaefdedd75a/internal/controller/postgrescluster/instance.go#L1314) · [Default spread](https://github.com/CrunchyData/postgres-operator/blob/0478c1dea748e6bc4cc382aba1210aaefdedd75a/internal/controller/postgrescluster/topology.go) · [Rollout candidate and budget](https://github.com/CrunchyData/postgres-operator/blob/0478c1dea748e6bc4cc382aba1210aaefdedd75a/internal/controller/postgrescluster/instance.go#L859) |
| OpenSearch Kubernetes Operator | One StatefulSet per node pool, with an application-aware restart and classical shard allocation or cluster-manager checks. [Pool reconciliation](https://github.com/opensearch-project/opensearch-k8s-operator/blob/b0be10474334e676c6044e7943322685af2e2d34/opensearch-operator/pkg/reconcilers/cluster.go#L235) · [Restart safety checks](https://github.com/opensearch-project/opensearch-k8s-operator/blob/b0be10474334e676c6044e7943322685af2e2d34/opensearch-operator/pkg/reconcilers/rollingRestart.go#L370) |

CloudNativePG is the closest reference when the operator must own Pod lifecycle end to end. The transferable idea is using application state to choose when to advance. Crunchy shows how to keep an application-wide rollout policy even when native controllers own the workload underneath. Neither implementation's default spread establishes the particular guarantee needed here, a configurable serving floor by role and AZ. PostgreSQL primary election and per-instance PVC management have no direct equivalent for object-store-backed shard ownership.

The [proposed workload design](multi-az-operator-design.md) applies the rollout lessons while keeping Pod creation and replacement in Kubernetes Deployments.
