# Why Karpenter can launch nodes that a Pod cannot use

Karpenter predicts what a new node will offer. The Kubernetes scheduler binds the Pod using the registered node's allocatable resources, existing Pod requests, and live scheduling constraints. A near-full-node OpenSearch Pod can pass Karpenter's prediction and still fail that second decision. If the Pod remains unscheduled and the next prediction still says it fits, provisioning can repeat. Whether that happens depends on what Karpenter learns from the node, which capacity remains in flight, and the cause of the mismatch. [Karpenter provisioning troubleshooting](https://karpenter.sh/docs/troubleshooting/#karpenter-incorrectly-computes-available-resources-for-a-node)

## Code path on AWS

| Step | What the source does |
| --- | --- |
| Pick up demand | Karpenter considers an unbound Pod that the scheduler marked `Unschedulable`, subject to exclusions such as preempting Pods, DaemonSet Pods, and mirror Pods. It computes candidate NodeClaims and kube-scheduler handles Pod binding. [Provisioning eligibility](https://github.com/kubernetes-sigs/karpenter/blob/05e212f98405a4a8cbee76c580cb4b737b3f62b2/pkg/utils/pod/scheduling.go#L97-L112) |
| Estimate node allocatable | The AWS provider starts with the EC2 instance shape. Its default VM memory deduction is 7.5% until observed memory is available. It models kubelet and system reservations and the hard eviction threshold. The pinned allocation path passes `evictionHard` into this calculation. The troubleshooting page also describes `evictionSoft` in its formula, so check the deployed revision before relying on either. [AWS instance sizing](https://github.com/aws/karpenter-provider-aws/blob/475815f556945b1ce8cf4f38b478e39523bcb772/pkg/providers/instancetype/types.go#L279-L315) · [Memory estimate](https://github.com/aws/karpenter-provider-aws/blob/475815f556945b1ce8cf4f38b478e39523bcb772/pkg/providers/instancetype/types.go#L526-L535) · [Default setting](https://github.com/aws/karpenter-provider-aws/blob/475815f556945b1ce8cf4f38b478e39523bcb772/pkg/operator/options/options.go#L73) · [Core allocatable calculation](https://github.com/kubernetes-sigs/karpenter/blob/05e212f98405a4a8cbee76c580cb4b737b3f62b2/pkg/cloudprovider/types.go#L353) |
| Account for workload and DaemonSets | The inspected core groups instance types by compatible DaemonSets within a NodePool, sums their effective requests and host ports, and considers them with the workload's requests when evaluating fit and offerings. Its resource helper uses Kubernetes Pod request calculation. [DaemonSet overhead groups](https://github.com/kubernetes-sigs/karpenter/blob/05e212f98405a4a8cbee76c580cb4b737b3f62b2/pkg/controllers/provisioning/scheduling/scheduler.go#L1010-L1092) · [NodeClaim fit](https://github.com/kubernetes-sigs/karpenter/blob/05e212f98405a4a8cbee76c580cb4b737b3f62b2/pkg/controllers/provisioning/scheduling/nodeclaim.go#L584) · [Pod request calculation](https://github.com/kubernetes-sigs/karpenter/blob/05e212f98405a4a8cbee76c580cb4b737b3f62b2/pkg/utils/resources/resources.go#L119) |
| Reconcile with the registered node | Karpenter uses the NodeClaim estimate before registration, fills missing resources from the claim during initialization, and uses the Node's allocatable once initialized. On AWS, the provider can learn a lower raw memory **capacity** from observed nodes. That cache is keyed by instance type and the NodeClass AMI set. It does not learn kubelet reservations or DaemonSet requests from this memory observation. [State node accounting](https://github.com/kubernetes-sigs/karpenter/blob/05e212f98405a4a8cbee76c580cb4b737b3f62b2/pkg/controllers/state/statenode.go#L485-L505) · [AWS memory observation](https://github.com/aws/karpenter-provider-aws/blob/475815f556945b1ce8cf4f38b478e39523bcb772/pkg/providers/instancetype/instancetype.go#L522-L548) · [Cache key](https://github.com/aws/karpenter-provider-aws/blob/475815f556945b1ce8cf4f38b478e39523bcb772/pkg/providers/instancetype/instancetype.go#L575) |

## Where a mismatch can come from

- **A node image or bootstrap changes the budget.** An AMI/instance-type combination can register less memory than predicted. Custom bootstrap can change kubelet reservations, maximum Pods, or disk setup. This is especially visible when one Pod uses nearly all the allocatable CPU or memory. Compare `NodeClaim.status.allocatable` with `Node.status.allocatable`, as well as the Pod's admitted requests. The `FailedConsistencyCheck` calculation in the pinned core compares raw capacity against the claim's predicted capacity for resources in the claim's requests and warns below 90%. A smaller gap or one caused by reservations can still prevent fit. [Resource discrepancy troubleshooting](https://karpenter.sh/docs/troubleshooting/#karpenter-incorrectly-computes-available-resources-for-a-node) · [NodeShape check](https://github.com/kubernetes-sigs/karpenter/blob/05e212f98405a4a8cbee76c580cb4b737b3f62b2/pkg/controllers/nodeclaim/consistency/nodeshape.go#L35-L58)
- **The DaemonSet rollout changes the budget.** The pinned core takes a cached representative Pod for each DaemonSet when one exists and otherwise uses the template. The cache picks the newest controlled Pod by creation time and refreshes periodically. The provisioner reapplies the template's required node affinity but keeps the cached Pod's requests. If a DaemonSet raises its memory or CPU requests, the estimator can still see the old requests until a new Pod is present and observed. It also models one representative per DaemonSet, while a surge rollout can temporarily run two Pods on a node. Those are prediction gaps visible from the code. Which Pod schedules first and whether a new node repeats the mismatch need a cluster reproduction. [Provisioner DaemonSet input](https://github.com/kubernetes-sigs/karpenter/blob/05e212f98405a4a8cbee76c580cb4b737b3f62b2/pkg/controllers/provisioning/provisioner.go#L560-L585) · [Representative selection](https://github.com/kubernetes-sigs/karpenter/blob/05e212f98405a4a8cbee76c580cb4b737b3f62b2/pkg/controllers/state/cluster.go#L700-L729) · [Cache refresh](https://github.com/kubernetes-sigs/karpenter/blob/05e212f98405a4a8cbee76c580cb4b737b3f62b2/pkg/controllers/state/informer/daemonset.go#L53-L88) · [DaemonSet rolling update API](https://kubernetes.io/docs/reference/kubernetes-api/workload-resources/daemon-set-v1/)
- **Bootstrap adds an unmodeled taint.** Karpenter documents a repeat-provisioning case with Cilium's temporary startup taint. A new node gets the taint, the workload cannot use the node yet, and Karpenter can request another. Declare the exact temporary taint in `startupTaints` and verify the bootstrap component that removes it. A taint that never clears is a bootstrap failure. Keep the permanent dedicated-node taint in the NodePool's regular `taints`. [Startup taints and the Cilium case](https://karpenter.sh/docs/concepts/nodepools/#cilium-startup-taint)
- **The real scheduler sees different constraints.** Pod slots, injected containers, RuntimeClass overhead, PVC topology, and node labels or taints can change the result. Check the admitted Pod and the actual node. In the historical Prometheus case, scheduler events listed several different failures across the fleet. The report's follow-up traced the undersized nodes to DaemonSets selected by labels that only appeared after bootstrap and confirmed the workaround. [Reporter confirmation](https://github.com/aws/karpenter-provider-aws/issues/5406#issuecomment-1874239824)

## How to identify the observed failure

Collect one timeline with the pending Pod UID and the role/AZ, the autoscaler's relevant launches, the registered Node IDs and labels, and the Pod's scheduler events. Karpenter exposes `Launched`, `Registered`, and `Initialized` on each NodeClaim. Correlate by pool, AZ, time, and nomination/events where available. A NodeClaim can reflect several Pods' demand and does not belong to the OpenSearch workload. [NodeClaim lifecycle](https://karpenter.sh/docs/concepts/nodeclaims/)

| Observation | First checks |
| --- | --- |
| No NodeClaim, or the claim fails to launch | Check pool limits, SKU eligibility in the required AZ, cloud quota and offerings, expected DaemonSet overhead, and storage or affinity requirements. An unsatisfiable pool or cloud shortage can leave the Pod pending without adding registered nodes. |
| Claim launched but no registered Node | Check node identity and bootstrap, API connectivity, and the provider's launch result. |
| Node registered but uninitialized | Check node readiness, startup taints, CNI readiness, and any expected extended resources or labels. |
| Node initialized but the Pod has `FailedScheduling` | Compare predicted and actual allocatable per dimension. Then account for assigned requests, including DaemonSets, available Pod slots, and the scheduler's reported constraints. Compare DaemonSet generations and bootstrap configuration before and after the failure. |
| Pod has a node assignment but does not start or become ready | Inspect volumes, images, CNI, kubelet events and Java readiness. This requires a different recovery path from a Pod that still needs a node. |
