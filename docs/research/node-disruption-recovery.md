# Recovering from node maintenance and loss

Treat the Java OpenSearch nodes as replaceable. The shared store holds durable state, while a running node holds a writer lease, in-flight work, or a warm search cache. Losing several nodes together can interrupt writes while ownership moves, reduce query capacity, and shift many cache misses to the object store. Plan for those losses even when no notice arrives. [Java operations and failure evidence](java-serverless-operations.md)

## How long a drain can wait

| Operation | Practical limit |
| --- | --- |
| GKE Standard surge upgrade | GKE respects the PDB and Pod grace settings for up to **one hour** while draining. Configure `maxSurge: 1` and `maxUnavailable: 0` for ordinary upgrades. Keep node pool upgrades sequential for the serving pools. New node readiness is a VM and Kubernetes milestone. Warm search capacity must be checked at the workload level. [GKE Standard cluster upgrades](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/cluster-upgrades) · [Surge strategy](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/node-pool-upgrade-strategies#surge-upgrades) |
| GKE Standard node-pool blue/green | Longer batch and node-pool soak times can delay final removal. The documented maximum combined soak is **seven days** for standard blue/green. At final deletion GKE bypasses PDBs for remaining Pods. Choose this for a planned operation that needs extra validation time, with quota for the overlapping pools. [GKE blue/green phases](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/node-pool-upgrade-strategies#phases-of-blue-green-upgrades) |
| GKE node auto-repair | GKE waits **one hour** for drain, then shuts down and recreates the node if drain has not finished. Several repairs can run in parallel. [GKE node repair process](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/node-auto-repair#node-repair-process) |
| EKS managed node group update | The default upgrade strategy creates capacity first and respects the group's `maxUnavailable`. Set it to `1` for serving pools. After **15 minutes** of unsuccessful drain the ordinary update fails with `PodEvictionFailure`. A forced update can delete the Pods. [EKS managed update behavior](https://docs.aws.amazon.com/eks/latest/userguide/managed-node-update-behavior.html) |
| EKS with Karpenter | Use an absolute `nodes: "1"` budget per NodePool for planned drift, and limit consolidation of serving nodes. Coordinate multiple NodePools because each has its own budget. A configured NodeClaim `terminationGracePeriod` bounds drain and can force Pod deletion. `expireAfter` can start many drains on nodes created together, and expiration and interruptions bypass the voluntary disruption budget. EC2 Spot normally gives **two minutes** of interruption notice. An EC2 event or sudden loss can end the opportunity to drain sooner. [Karpenter disruption budgets, deadlines, and interruption](https://karpenter.sh/docs/concepts/disruption/) |

## Start replacements before draining

For planned maintenance, start with one serving Pod retirement in flight across the OpenSearch instance. Use the platform's node upgrade or drift limits for external maintenance and the operator's overall budget for actions it owns. A zonal PDB restricts eviction within its role and zone. Coordinate maintenance across pools through the platform and the operator's availability status. The eviction API rejects a Pod covered by overlapping PDB selectors, so a second PDB matching the whole fleet cannot add a global eviction budget. [Kubernetes PDB selector rules](https://kubernetes.io/docs/tasks/run-application/configure-pdb/#arbitrary-workloads-and-arbitrary-selectors)

For example, keep two warm search Pods per AZ and set `minAvailable: 2` for each search AZ if two must keep serving. In a planned window the platform makes an extra dedicated host eligible in that AZ. The operator starts a third Pod on capacity outside the drain set and checks it has joined, warmed sufficiently, and serves through the production search path. A Ready Pod matching the same PDB selector raises the healthy count to three, allowing one voluntary eviction. After eviction, keep the two healthy Pods serving and restore enough capacity for the next drain. Ensure the PDB counts app-eligible Pods through Kubernetes readiness. A staged Pod outside the serving selector or a replacement VM with no Pod cannot protect the serving floor. Apply the same sequence to indexing with the writer admission and handover checks for that role.

The platform can initiate a planned operation after the operator reports the required headroom. An early maintenance hint can start the same preparation, using the [namespaced signal](#detecting-disruption-with-minimal-permissions). A PDB-blocked eviction can leave the old Pod running with no deletion timestamp. Enable the temporary replica before waiting for an eviction. Use the drain window for endpoint removal and Java shutdown, with a margin for platform delays. If there is too little notice to launch and warm a Pod, use already-serving spare capacity, hold planned changes, and recover in bounded waves. Never count a Pod still bound to a node in the drain set as surviving capacity.

### Warm capacity during GKE upgrades and repair

Keep `cluster-autoscaler.kubernetes.io/safe-to-evict: "false"` on the Pod for its lifetime. It blocks the Cluster Autoscaler from selecting the node for ordinary scale-down. GKE can still drain and recreate the node for an upgrade or auto-repair. In autoscaled blue/green, the annotation protects the Pod from autoscaler scale-down during the pause. GKE drains the remaining blue nodes in the later upgrade phase. A standard surge upgrade honors PDB and Pod grace settings for up to one hour. Auto-repair can shut down a node after a one-hour drain wait and can repair several unhealthy nodes in parallel. [GKE Cluster Autoscaler](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/cluster-autoscaler) · [GKE node upgrade strategies](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/node-pool-upgrade-strategies) · [GKE auto-repair](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/node-auto-repair#node-repair-process)

For a controlled upgrade, the platform initiates the drain only when the operator reports warm capacity outside its scope. For an automatic drain without notice, maintain [running reserves by role and AZ](#configure-warm-spare-capacity-by-role-and-az) and replenish them at the first disruption signal. For example, three warm search Pods with `minAvailable: 2` can sustain one ordinary eviction. The next healthy Pod eviction is blocked until another Pod becomes Ready or the platform proceeds under its own drain deadline. Simultaneous forced failures can consume more capacity than the PDB or chosen reserve covers. [PDB health and eviction rules](https://kubernetes.io/docs/tasks/run-application/configure-pdb/#healthiness-of-a-pod)

Use application readiness to decide when the replacement counts toward the PDB. For search use the [warm-up result](#verify-that-a-search-pod-is-warm). Validate indexing independently using a current lease and capacity for writer handoff or replay. [Java request routing and recovery](java-serverless-operations.md)

### Verify that a search Pod is warm

The pinned Java shell needs a small status change for a dependable warm-up gate. Enable `serverless.search.warm_on_join` on search Pods where the policy is used. It defaults to `false`. The current `/_serverless/ready` reflects whether the node may serve searches. Search warm-up can set that flag after the deadline or a failure. Java also uses the flag to advertise the search role in the node's lease, so keep existing routing behavior when adding a separate warm-up status. [Search settings](https://github.com/huyz0/OpenSearch/blob/e71d42331a3ec82ec01109a5bb42d6a9a9162a5c/serverless/shell/src/main/java/org/opensearch/serverless/node/SearchSettings.java#L66-L86) · [Readiness handler](https://github.com/huyz0/OpenSearch/blob/e71d42331a3ec82ec01109a5bb42d6a9a9162a5c/serverless/shell/src/main/java/org/opensearch/serverless/rest/ServerlessReadyHandler.java#L58-L71) · [Warm-up fallback](https://github.com/huyz0/OpenSearch/blob/e71d42331a3ec82ec01109a5bb42d6a9a9162a5c/serverless/shell/src/main/java/org/opensearch/serverless/warm/SearchWarmup.java#L68-L104)

- `/_serverless/stats` exposes `block_cache.hits`, `misses`, and `bytes_fetched`. These counters measure accesses and fetches, rather than coverage of the assigned hot set. A cold or idle Pod can have very few samples. Peer-copied blocks do not increase `bytes_fetched`. `BlockCache` tracks copied and resident bytes internally, but byte totals also lack the target hot-set denominator. [Stats fields](https://github.com/huyz0/OpenSearch/blob/e71d42331a3ec82ec01109a5bb42d6a9a9162a5c/serverless/shell/src/main/java/org/opensearch/serverless/rest/StatsHandler.java#L532-L540) · [Cache accounting](https://github.com/huyz0/OpenSearch/blob/e71d42331a3ec82ec01109a5bb42d6a9a9162a5c/serverless/shell/src/main/java/org/opensearch/serverless/store/BlockCache.java#L228-L273)
- The `search_warmup_finished` log includes blocks copied and shard-open results. It can appear after timeout and lacks a coverage denominator. The peer-copy threshold callback can also fire when copying ends without reaching the target, so publishing that callback as success would be inaccurate. [Warm-up logging](https://github.com/huyz0/OpenSearch/blob/e71d42331a3ec82ec01109a5bb42d6a9a9162a5c/serverless/shell/src/main/java/org/opensearch/serverless/warm/SearchWarmup.java#L75-L104) · [Threshold callback](https://github.com/huyz0/OpenSearch/blob/e71d42331a3ec82ec01109a5bb42d6a9a9162a5c/serverless/shell/src/main/java/org/opensearch/serverless/transport/CacheWarmCopy.java#L565-L602)
- A representative search and cache hit/miss deltas can validate performance during qualification if execution on the replacement is confirmed. A request sent to the Pod can still be forwarded to a peer. Use existing metrics for observation during a canary while holding voluntary drains to the existing warm reserve. [Java request routing and recovery](java-serverless-operations.md)

Expose one cheap node-local status snapshot that the operator can read directly from the target Pod. Record whether warm-up is in progress, the configured threshold was actually met, or readiness was released after a timeout or failure. Include the selected hot-set block count, how many of those blocks are locally held at evaluation, and enough peer and shard-open counts to distinguish an empty sample or missing peers from a completed warm-up. A valid cold start with no hot data needs an explicit policy. Distinguish initial fallback from any later verified warm completion, and reset the snapshot for the new process on restart. Preserve the current readiness response and peer routing behavior. The operator must treat missing warm-up status on an older Java image as unknown. [Peer copy accounting](https://github.com/huyz0/OpenSearch/blob/e71d42331a3ec82ec01109a5bb42d6a9a9162a5c/serverless/shell/src/main/java/org/opensearch/serverless/transport/CacheWarmCopy.java#L431-L507)

For a planned retirement, the operator can wait for this signal before proceeding. For a provider drain that relies on the PDB, use a local readiness probe that checks the current Java process, because Kubernetes counts `Ready=True`. An operator-managed gate is supplemental. Its custom Pod condition can survive a container restart under the same Pod UID. If every Pod starts cold during recovery, use the configured degraded-serving policy and keep warm capacity visible separately. Exercise success, threshold shortfall, timeout followed by completion, peer failure, empty hot sets, and restart while the controller is delayed. [Readiness and shutdown design](../design/traffic-and-security.md#readiness-and-shutdown) · [Kubernetes Pod readiness](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/#pod-readiness) · [PDB health](https://kubernetes.io/docs/tasks/run-application/configure-pdb/#healthiness-of-a-pod)

| --- | --- |

The operation notice is unsuitable for selecting the next victim by name. If the PDB is still blocking, the signal may give the operator time to add bounded surge capacity. The timeout notice is an escalation. It arrives when GKE is going to force deletion. | Pod watch | The managed Pod's `spec.nodeName` tells us which host it uses as soon as the Pod has bound. For controlled maintenance, the platform publishes the target pool or old node generation and waits for the operator to report that an extra eligible Pod is serving outside that target. A node name is optional. For example, a Pod can require the label of a qualified replacement pool in the same AZ and retain the normal role, Service and PDB selectors. The operator can check binding and app readiness using its Pods. The platform owns the scope and starts draining only after the capacity check. Use one such surge wave at a time. For provider-initiated maintenance that does not wait for the workload, react to scoped warnings when possible and keep an already-warm reserve for events that arrive late or with no notice.

Kubelet readiness probes tell Kubernetes when the **replacement** qualifies for traffic and PDB availability. A custom readiness gate, if needed, uses a namespaced `pods/status` permission to publish a condition. A local HTTP readiness probe needs no Kubernetes API access. Neither provides a notification of future drains. Keep the old Pod serving while the replacement warms. Flipping the old Pod unready in advance can remove it from traffic and reduce the healthy count that the PDB uses. `preStop` and JVM shutdown remain cleanup mechanisms after termination starts. ## Detecting disruption with minimal permissions

Build the default on the existing watch for managed Pods in the workload namespace. Observe `DisruptionTarget` when available, `deletionTimestamp`, changes in `Ready`, and Pod disappearance. `DisruptionTarget` can distinguish eviction API, taint eviction, or some kubelet terminations. These signals can arrive after the disruption starts. Combine them with live Java readiness, lease and peer signals, because the Kubernetes view can lag an abrupt loss. Require fresh evidence of serving capacity before allowing planned retirement. Report unknown capacity when observations are stale. [Kubernetes Pod disruption conditions](https://kubernetes.io/docs/concepts/workloads/pods/disruptions/#pod-disruption-conditions)

The local shutdown path needs no Kubernetes API credentials. Kubelet's `SIGTERM` already invokes the Java shutdown hook when the signal reaches the JVM. Verify the image launcher forwards it and the Pod grace period covers the measured drain. If the workload needs an explicit hook, use a short, bounded `preStop` that invokes a local, authenticated drain action. Coordinate it with Java's built-in search drain so the request is idempotent and leaves time for writer handover. The `preStop` duration comes out of the Pod's shutdown grace period. A hard node loss or forced shutdown can skip the hook. Avoid relying on it to create or wait for another Pod. [Container lifecycle hooks](https://kubernetes.io/docs/concepts/containers/container-lifecycle-hooks/) · [Java shutdown sequence](https://github.com/huyz0/OpenSearch/blob/e71d42331a3ec82ec01109a5bb42d6a9a9162a5c/serverless/shell/src/main/java/org/opensearch/serverless/shell/ServerlessBootstrap.java#L407)

| Optional signal | Where it comes from | How the OpenSearch operator can consume it |
| --- | --- | --- |
| GKE upgrade or security notification | The platform configures GKE Pub/Sub notifications. `UpgradeEvent` starts when the operation begins. A `SecurityBulletinEvent` is a security advisory. Scheduled cluster upgrade notifications, where enabled, can provide earlier notice. | Consume scope, operation ID, phase and expected window from a platform publisher. A bulletin can prompt preparation. Require a scoped schedule or evidence of a drain before creating replacement demand. [GKE notification types](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/cluster-notifications) |
| EC2 scheduled maintenance or interruption | The platform configures AWS Health/EventBridge and Karpenter's SQS interruption handling. Karpenter also publishes Kubernetes Node events for supported interruptions. | Consume a scoped maintenance hint from the platform, including node identity and deadline if known. If using cloud events, configure a separate delivery target for alerts or the publisher. Independent consumers should not compete with Karpenter for the same queue messages. [EC2 events](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/monitoring-instances-status-check_sched.html) · [Karpenter interruption handling](https://karpenter.sh/docs/concepts/disruption/#interruption) |
| Live node state | An optional platform watcher observes cordon, relevant taints and `NodeReady`, and correlates Nodes to workload Pods. | A namespaced Pod watch does not read Node objects. Keep cluster-scoped reads in the platform component if needed, or explicitly enable an optional read-only Node watcher where the deployment allows it. A cordon alone is a signal to investigate or hold planned changes while the Pod can still serve. [Kubernetes RBAC scopes](https://kubernetes.io/docs/reference/access-authn-authz/rbac/#role-and-clusterrole) |

If early warnings are useful, let the platform publish a small current snapshot in a pre-created, namespaced ConfigMap. Give the OpenSearch operator `get` on that named object, and the platform publisher update permissions only on the named object in each opted-in namespace. Keep the cloud subscriber identity with the platform. Include an operation ID, role/AZ or pool, optional node UID, phase, expiry and deadline if known. Ignore stale or unrelated hints and deduplicate retries. A hint can pause voluntary work or authorize bounded warm-up within the existing capacity budget. Live Pod and application state determines when a role becomes unavailable or resumes. Refresh or expire the hint even if a completion event is lost. Namespaced Pods and the local hook remain sufficient to run recovery when the optional publisher is unavailable. ## Automatic drains without a platform publisher

With only namespace access, recovery can start on the first observed `DisruptionTarget`, `deletionTimestamp`, or confirmed loss of serving capacity. A PDB can reject the eviction before the Pod changes at all. Once the eviction is accepted, a terminating Pod normally stops receiving new Service traffic even while its Java process still has time to shut down. The GKE one-hour allowance describes how long the provider honors drain protections. It does not describe how long the old Pod remains in service after the operator sees a termination signal. Use these signals to refill capacity rather than to guarantee a warm handoff from the particular Pod that is leaving. [Eviction responses](https://kubernetes.io/docs/concepts/scheduling-eviction/api-eviction/) · [Endpoint behavior during termination](https://kubernetes.io/docs/concepts/workloads/pods/pod-termination/) · [GKE drain limits](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/cluster-upgrades#how_nodes_are_upgraded)

For a role/AZ that must continue serving at its floor, maintain a standing reserve of running, app-eligible Pods. For example, keep **three warm search Pods per AZ** with a PDB floor of **two**. The first voluntary eviction can proceed with two warm survivors. The PDB blocks another voluntary eviction in that role/AZ until a replacement is Ready. With a target and PDB floor both set to two, an ordinary drain can stall before the Pod watch exposes a signal. Apply the reserve only where measured serving targets justify it. Separate zonal budgets may each allow an eviction at the same time. Abrupt loss and forceful provider deadlines can exceed the reserve. [Kubernetes PDB behavior](https://kubernetes.io/docs/concepts/workloads/pods/disruptions/#pod-disruption-budgets)

On a disruption signal, reconcile a single replacement against the affected role/AZ's desired capacity, counting warmups already in flight. Start it while the old Pod is terminating when surge capacity allows. Use the existing Pod watch and namespaced Pod creation permissions. The scheduler places new Pods on eligible nodes and the provisioner can add capacity as needed. Prioritize restoring the serving floor ahead of replenishing spares, and keep the existing limits on pending provisionable Pods and concurrent warmups. A disruption condition can be cleared without deletion. If the old Pod remains healthy, reconcile any temporary surge through the normal readiness and retirement checks. [Pod disruption conditions](https://kubernetes.io/docs/concepts/workloads/pods/disruptions/#pod-disruption-conditions) · [Provisioning limits](dedicated-node-placement.md#limit-the-effect-of-provisioning-failures)

Measure elapsed time from the first observable Pod signal to the replacement serving under load. Run the test with a qualified empty host already available, with a cold node launch, and with simultaneous losses. Empty nodes can shorten scheduling and startup. Running warm Pods keep serving during the entire replacement window. Client failures and latency during the test determine whether the chosen reserve is sufficient.

## Configure warm spare capacity by role and AZ

Use the [existing placement design](multi-az-operator-design.md#placement-contract) of a desired replica count and minimum serving count for each role and AZ. The replica count includes spare capacity. The operator keeps the entire desired set running and serving. With all replicas eligible, the difference between `replicas` and `minServing` is the nominal spare count. Once health changes, report the current surplus using the observed eligible count. Validate `0 <= minServing <= replicas` and translate the serving floor to the integer `minAvailable` of that role and AZ's PDB. [PDBs for operator-managed Pods](https://kubernetes.io/docs/tasks/run-application/configure-pdb/#arbitrary-workloads-and-arbitrary-selectors)

The field names below illustrate the proposed API. The actual counts need load and failure testing.

```yaml
spec:
  pools:
    search:
      zones:
        ap-southeast-2a: { replicas: 3, minServing: 2 }
        ap-southeast-2b: { replicas: 4, minServing: 2 }
    ingest:
      zones:
        ap-southeast-2a: { replicas: 2, minServing: 1 }
        ap-southeast-2b: { replicas: 3, minServing: 2 }
```

In this example, AZ `2a` has one spare search Pod and one spare indexing Pod when all five Pods are eligible. AZ `2b` has two search spares and one indexing spare across seven Pods. With one Pod per node, provision for five and seven steady nodes respectively, plus the separately budgeted rollout surge. A larger replica surplus also permits more healthy evictions under the PDB alone. Keep the separate per-NodePool and operator disruption limits for planned work.

Every search replica joins normally and warms its cache. Check workload latency and cache miss load after the expected loss, since search warmup can time out and cache coverage is distributed. Every indexing replica has a live lease and can accept ownership. Measure enough unused writer capacity on the survivors for normal writes and takeover replay after a loss. Running an extra writer gives us takeover capacity. The Java shell still relies on fencing and replay for shards whose owner disappears. [Java readiness, warm-up, and writer recovery](java-serverless-operations.md)

Maintain the desired replica count as the operator replenishes a disrupted group. Retire a planned surge only after reaching the normal target with healthy replicas. Keep the desired reserve in the steady count used by any future autoscaler. [Karpenter policy for dedicated pools](dedicated-node-placement.md#keep-warm-pods-through-consolidation) · [GKE Standard scale-down protection](dedicated-node-placement.md#keep-warm-pods-on-gke-standard)

## Recover from the loss of one AZ

Size the fleet so that losing its largest AZ still leaves enough warm search capacity and indexing capacity for peak traffic. For example, three search Pods and two indexing Pods per AZ across three equal zones gives nine search and six indexing Pods. Losing one zone leaves six search and four indexing Pods. With even redistribution and unchanged traffic, each survivor handles 1.5 times its previous share before accounting for cache misses, remote reads and writer replay. Qualify those survivors under load before relying on any scale-out. The Kubernetes control plane, operator, ingress and shared store must remain reachable from surviving zones. Use a regional control plane for GKE Standard and place redundant operator and ingress replicas across zones. [GKE regional clusters](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/regional-clusters) · [EKS reliability guidance](https://docs.aws.amazon.com/eks/latest/best-practices/reliability.html)

1. **Detect and hold.** Group the operator-owned Pods by their assigned role and AZ. Correlate Kubernetes readiness, independent host assignments and fresh Java serving or lease observations. Several hosts losing contact in the same AZ while peers in other zones still serve is evidence of zonal unavailability from the workload's perspective. A single failed probe or store errors across the fleet do not establish an AZ outage. Report the affected AZ, desired and observed capacity, and the evidence. Hold planned retirements, downscales, certificate rolls and application promotion while the serving floors are under pressure. [Java readiness and lease signals](java-serverless-operations.md#health-performance-and-diagnostics)
2. **Keep traffic on the survivors.** Keep the production search and indexing Services targeting their current serving revision across AZs. Verify ingress and load-balancer health checks stop sending traffic to unreachable endpoints and allow failover across zones. With a supported Service dataplane, `PreferSameZone` gives locality with cluster-wide fallback once same-zone endpoints are unavailable. Node-local-only policy has different semantics. Test how long unreachable endpoints can still appear healthy from the ingress. Within Java, remaining readers cover searches with their caches and the shared store. Let Java detect expired writer leases, fence old owners and replay WAL on surviving writers. The operator does not reassign shards or release another node's lease. Affected writes can fail or time out before ownership recovers. [Kubernetes Service traffic distribution](https://kubernetes.io/docs/reference/networking/virtual-ips/#traffic-distribution-control) · [Java recovery evidence](java-serverless-operations.md#evidence-in-the-branch)
3. **Restore capacity without creating a launch or cache storm.** Keep the permanent replica targets for the failed AZ visible and bound the failed-zone Pod demand with the existing provisioning guard. Where explicitly enabled, create temporary extra replicas in surviving AZs with their actual AZ affinity and advertised Java zone. Trigger emergency scale-out from measured search saturation, write admission and recovery backlog within role/AZ and overall caps. Bound concurrent search warmups and watch object-store throttle, latency and errors. Prioritize serving floors over restoring the reserve. An outage in the store or its network path calls for preserving the fleet and handling overload rather than restarting Pods across AZs. [Dedicated-node provisioning guard](dedicated-node-placement.md#limit-the-effect-of-provisioning-failures) · [Search warm-up verification](#verify-that-a-search-pod-is-warm)
4. **Bring the AZ back gradually.** After stable recovery observations, rebuild the original per-zone targets in waves. Verify fresh leases, search warm-up and query coverage before removing temporary survivor capacity. Java continues to manage existing shard ownership. Resume unrelated work after the required floors and workload health are stable. Record the interval from unavailable endpoints to healthy routing, writer ownership and write recovery per affected shard cohort, search errors and latency, store load, and acknowledged and unknown write outcomes. Test a sudden loss or partition of the largest zone, including while the operator is in the middle of a rollout. [Multi-AZ verification cases](multi-az-operator-design.md#verification-that-distinguishes-the-designs)

### Route around failed endpoints behind an ALB

For an EKS deployment with a separate ingress proxy, the request path is `client → ALB → ingress Pod → search or indexing Service → OpenSearch Pod`. The two hops have different targets and must each remove failed endpoints. The platform owns ALB and ingress configuration. The OpenSearch operator manages role Services, workload readiness and serving capacity in its namespace. When AWS Load Balancer Controller routes the ALB directly to the two OpenSearch Services, the service Pods are the ALB targets and the intermediate proxy checks do not apply. [AWS Load Balancer Controller target types](https://kubernetes-sigs.github.io/aws-load-balancer-controller/latest/guide/ingress/annotations/#target-type)

| Hop | Health and failover behavior |
| --- | --- |
| ALB to ingress | Use `ip` targets where the EKS networking supports them, so the ALB checks the ingress Pods directly. Spread ingress replicas across the serving AZs and keep cross-zone routing enabled at the target group level. Point the health check at a fast readiness path on the registered proxy. The proxy must accept the Host header used by ALB health checks, which contains the target IP. Avoid a health route that becomes unhealthy on every ingress replica because a single upstream or shared dependency reports a fault. Test end-to-end application health through the actual client routes separately. [Target types](https://kubernetes-sigs.github.io/aws-load-balancer-controller/latest/guide/ingress/annotations/#target-type) · [ALB cross-zone routing](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/edit-target-group-attributes.html#cross-zone-load-balancing) · [ALB health checks and Host headers](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/load-balancer-troubleshooting.html) |
| Ingress to OpenSearch | Send search and indexing traffic to their separate production Services. Leave `publishNotReadyAddresses` disabled for these Services. Verify the ingress dataplane removes unready OpenSearch endpoints and has no hard local-only restriction for these routes. Use role-aware Kubernetes readiness and the [search warm-up gate](#verify-that-a-search-pod-is-warm) where required. If the ingress supports it, eject upstreams on transport failures and allow a bounded retry to another endpoint for replay-safe searches before returning a response. Use short upstream connect deadlines chosen from measurements. Preserve normal application errors and the semantics of indexing requests whose outcome is unknown. [EndpointSlice readiness](https://kubernetes.io/docs/reference/kubernetes-api/discovery/endpoint-slice-v1/#EndpointConditions) · [Service traffic policy](https://kubernetes.io/docs/reference/networking/virtual-ips/#traffic-policies) |

For AWS Load Balancer Controller, the following is an illustrative Ingress annotation fragment. Use an ingress health path that actually returns `200` on the configured health port. Test the interval, timeout and thresholds under load. A five-second interval and two consecutive failures are a starting point for the test, not a failover-time guarantee. [Controller annotation reference](https://kubernetes-sigs.github.io/aws-load-balancer-controller/latest/guide/ingress/annotations/#health-check) · [AWS target group health settings](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/target-group-health-checks.html)

```yaml
metadata:
  annotations:
    alb.ingress.kubernetes.io/target-type: ip
    alb.ingress.kubernetes.io/healthcheck-path: /readyz
    alb.ingress.kubernetes.io/healthcheck-interval-seconds: "5"
    alb.ingress.kubernetes.io/healthcheck-timeout-seconds: "2"
    alb.ingress.kubernetes.io/unhealthy-threshold-count: "2"
    alb.ingress.kubernetes.io/success-codes: "200"
```

For planned ingress replacement, enable the AWS Load Balancer Controller readiness gate on the Pods that are ALB targets. Set up its namespace label and matching Service and TargetGroupBinding before creating the Pods. Wait for the new ingress target to become ALB-healthy before retiring the predecessor. Coordinate deregistration and Pod shutdown grace so existing connections have time to finish. For OpenSearch Pods behind that ingress, wait for application readiness and allow endpoint removal to reach the proxy before hard shutdown. [AWS readiness gate setup](https://kubernetes-sigs.github.io/aws-load-balancer-controller/latest/deploy/pod_readiness_gate/) · [ALB deregistration](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/edit-target-group-attributes.html#deregistration-delay)

Abrupt failure can interrupt in-flight requests and blackhole new ones until the health checks or endpoint updates converge. ALB can fail open when all registered targets in a group are unhealthy, so keep healthy ingress capacity in surviving AZs. Bounded retries to the ALB from clients can cover some failures on the first hop. Retries at ingress can only cover failures on the second hop. Qualify both with separate sudden ingress-node, OpenSearch-node, and whole-AZ loss tests under live test traffic. Record response timeouts as well as HTTP codes. Compare ALB-generated 5xx with responses from its targets, and correlate ingress logs with endpoint removal and Java writer recovery. [ALB target health and fail-open](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/target-group-health-checks.html) · [ALB CloudWatch metrics](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/load-balancer-cloudwatch-metrics.html)

## Protecting serving capacity and cache

1. **Size for surviving capacity.** Pick a failure target for each role, such as the largest one-AZ loss or a specified concurrent node loss at peak. Measure whether surviving eligible indexing capacity can absorb ownership and replay, and whether warm search capacity can meet the latency target under the resulting store load. For six equal search nodes spread `2/2/2`, losing one AZ leaves four warm nodes before recovery. Check peak search against those four with cold misses and forwarding overhead included. Count running, qualified spare Pods separately from empty node capacity. Empty nodes shorten startup while warm Pods can absorb traffic immediately. Use regular capacity for the serving floor and consider Spot for excess capacity.
2. **Pause operator-driven disruption and preserve traffic.** When a relevant maintenance operation is active or serving capacity falls below a floor, pause planned retirement, scale-down, and app blue/green promotion. Keep healthy endpoints serving. Restore the role and zone counts as qualified capacity returns. A hard zonal target may remain unmet through an outage. Allow healthy-zone routing where configured, with any extra survivor capacity explicitly bounded. Continue critical recovery within the dedicated-node provisioning limits and their no-progress checks. [Multi-AZ placement](multi-az-operator-design.md#placement-contract) · [Bounded provisioning](dedicated-node-placement.md#limit-the-effect-of-provisioning-failures)
3. **Use graceful handover when possible.** For a planned replacement the operator controls, stage and verify a successor before retiring the old Pod. Java can drain search and hand writer ownership over during shutdown. On abrupt loss, Java's lease expiry, fencing and WAL replay determine when affected writes can resume. Count failed and unknown write outcomes separately from acknowledged writes, and use idempotent client retries where the API supports them. Keep liveness independent of shared-store health so a store slowdown does not trigger synchronized restarts. [Java recovery and readiness](java-serverless-operations.md)
4. **Warm search in waves.** Use Java's warm-on-join and its existing search readiness signal. Warm-up can complete at its timeout, so check representative queries, latency, and store load before advancing voluntary waves. Bound concurrent new warmups so background fetches and writer replay leave room for serving queries. Make the application fallback after a warm-up timeout explicit and test it under store throttling. Any gradual routing of traffic to cold Pods needs an ingress or application capability that supports it. A regular Kubernetes Service uses endpoint eligibility and has no per-Pod warm-up weights. [Java warm-up](https://github.com/huyz0/OpenSearch/blob/e71d42331a3ec82ec01109a5bb42d6a9a9162a5c/serverless/shell/src/main/java/org/opensearch/serverless/warm/SearchWarmup.java#L27-L44) · [Kubernetes Services](https://kubernetes.io/docs/concepts/services-networking/service/)

Report serving, draining, unavailable, and warming counts by role/AZ. Record maintenance scope and time if known, lost-node count, lease and replay timing, store errors and throttling, cache warmup timeouts, and search and indexing error and latency changes. Test a drain with advance notice, an interrupted hook, and simultaneous abrupt node or AZ loss during traffic. Repeat under slow object-store access and during an application rollout. Verify the surviving capacity and the time to recover against explicit search and write targets. Include one end-to-end GKE node upgrade and one EKS interruption exercise for the chosen configurations. This is design and source review. Live platform behavior and recovery targets still need qualification.
